# Penmoss for Android: for contributors

**Installing and using the Android app is in the user docs: [Install on Android](https://penmoss.app/docs/install/android/), [More devices](https://penmoss.app/docs/more-devices/#android) and [The Android app](https://penmoss.app/docs/android/).** This page keeps how it is built, tested on the Pixel and shipped.

The Android app (T32–T35, Milestone 2) is a native Kotlin/Compose shell around the shared editor, which runs in a WebView. This page covers building it, installing it on the Pixel, and shipping it through a Google Play internal testing track (D21). Decisions: A280–A294 (T32), A300–A315 (T33), A320–A331 (T35), A335–A349 (T34) and A352–A357 (T38) A410–A415 (T40 P1a), A416–A419 (T40 P1b), A590–A595 (the App Link sign-in and Play releases), A691–A692 (native symbols, publishing from the worker) A870–A885 (git notebooks, T50 G7 and G8) and A1040–A1049 (git notebooks only, T59) in [`decisions.md`](decisions.md).

The app runs on Android 17 (API 37) and later only (A835): `minSdk` and `targetSdk` are both 37. The Play listing's device requirements follow from the bundle's `minSdk`; nothing else to change there.

## Git notebooks only (T59, D48, D49)

Since T59 the app talks to no Penmoss server. Every note is in a git notebook (a private GitHub repository, below), and nothing else is on the phone:

- **First run.** With no git notebook, the app's first screen says Penmoss keeps your notes in git notebooks and asks to add one (from a private repository) or create one (point Add at an empty private repository and name it). There is no sign-in, no account and no personal notes anywhere. With notebooks, the first screen lists them; each opens in a task of its own (A1040).
- **Links and the launcher.** A `penmoss://note/<id>` link opens the note in the notebook whose Room cache has it, else the Journal notebook; Today, This week, New note and Search from the launcher open the Journal notebook (the one picked, else the first). With no notebook they open the first screen.
- **Settings.** Settings, opened from a notebook, are Appearance, Display, Symbols, Git notebooks, Daily notes, Quick capture, Keyboard shortcuts, Sync and storage and About. Device settings (mode, theme, shortcuts, capture destination) live in the Journal notebook's `device` map (A1014); with no notebook they show their defaults and cannot change. Quick Access pins are each notebook's own.
- **Feedback** goes to GitHub with the phone's own GitHub token (A1010–A1012). What waits or was refused is listed in Settings → About (A1046).
- **Gone with the server (A1041, A1042):** sign-in and the token vault, the personal sync and its background runs, Devices and agent tokens, Git mirror, Status and the server's error reports, the admin owner check for server requests, Send to… on comments, Retry uploads and Manage notebooks, the App Link and `penmoss://auth/callback`, and the build's `APP_ORIGIN`/`API_ORIGIN`. The phone's owner check stays for git notebooks (A855, A877).

The sections below keep how each part first came, on the Penmoss server. The same Kotlin sync pass, Room cache and editor run in each git notebook: the notebook's engine page answers the server's routes (`LocalGitApi`, A880), so "the server" in them is now that page. Their Pixel walk-throughs of server-only screens are removed.

How it fits together:

- **Sync (A280, A281, A286, A289).** Kotlin asks `/sync/tree` for the folder tree and `/sync/changes` for changed notes, then exchanges note content through `/sync/batch` as opaque Yjs updates. It never reads them: it keeps the state vector the server returns as a cursor and sends it back. Edits the editor makes are stored as pending updates and uploaded, at most 200 per note per request; the server's reply replaces those it applied. Each edit is stored with the epoch of the copy it was made on, and one made before a restore is kept apart, never uploaded (A291).
- **Editor (A282, A293).** The WebView loads the page from the APK at `https://appassets.androidplatform.net/assets/editor/index.html`. The page owns the open note's Yjs document. It gets the stored updates from Kotlin and sends back every edit, merged until typing pauses (at most every 2 s). It has no token and no network access: a strict CSP, and a `WebViewClient` that refuses every request but the editor's own files.
- **Writing (T33, A300–A307).** The note screen has a native formatting bar above the keyboard, and Back closes the editor's open menu first. The page completes `[[` links from the phone's notes, and a link to a new note works offline. Pictures can be pasted or picked from the photo picker; they are stored on the phone, uploaded when it can, and shown offline. The editor and the native screens use the theme chosen in Settings → Appearance. Edits a restore or a deletion kept apart become a conflict copy the next time a note is open, once no editor can still add to them (A309). Edits no copy can be made of are kept on the phone, and Settings says how many there are.
- **Background sync (T35, A320–A331).** WorkManager runs the same Kotlin sync pass about once an hour, and once more after the app leaves the screen with something unsent, waiting for a network when there is none, so the phone catches up as soon as it is back online. There is no WebView in the background; it moves the same opaque bytes. Runs need a network and a battery that is not low. They skip under battery saver, and under Data Saver on mobile data. On a metered network a run sends the phone's edits and refreshes notes the phone already has, at most 100 notes a run, and fetches no note the phone has never had: those wait for Wi-Fi or for the app to be opened. A run never overlaps a pass in front, and a run Android stops cancels its request at once. The open note checks for changes every 10 s only while the app is in front. Edits a background run keeps apart (a restore or deletion elsewhere) stay on the phone, Home says how many notes hold them, and they become conflict copies the next time a note is open.
- **Quick capture (T34, A335–A349).** Penmoss is in the share sheet for text, links and pictures, and has a Quick Settings tile and a home-screen widget. Each opens a capture sheet over the current app: the text, the pictures, and the same two destinations as the web and Mac apps (today's note under `## Captures`, or a new note in Inbox), starting on the one last chosen in any app. Save stores the capture on the phone at once, offline too; sync sends it to `POST /api/capture`, after its pictures, and the server adds it with the same rules as the web and Mac capture. A shared web page is saved as its title and address. A capture that cannot go as it is waits in a list Home opens, to copy, try again or discard; nothing captured is dropped unasked.
- **Organising (T38, A352–A363).** A note moves to another folder from the note screen's menu (**Move to folder…**) or with a long press in any list, through a picker showing the top level and the nested tree. The move shows at once and is filed with `POST /api/notes/:id/move` when the phone can reach Penmoss, by the queue that files the notes the phone makes. A move never brings back a note trashed meanwhile, and never undoes a move made on another device that the phone had not seen; signing out keeps moves still to send. **Tags…** in the same menu lists the note's frontmatter tags, removes them and adds new ones, with suggestions from `/api/tags` kept for offline. The editor page changes the note's document, as the web's tag chips do, so a tag change is stored and synced like typing. **New note** is made by the editor page, offline too: from Home it asks which folder (top level by default); a folder's own **New note** button makes it in that folder.
- **Settings (T40 P1a, A410–A415).** Settings is a list of sections: Appearance (mode, theme, note width), Daily notes (time zone and templates), Quick capture, Sync and storage, and This phone. The phone reads the settings in `/sync/tree` and changes them with `PUT /api/settings`, which runs the web's own `setSetting` and rules on the server; Kotlin never writes the WorkspaceDoc. A change shows at once, offline too, and waits in Room until a pass sends it, first thing in the pass. A setting changed on another device since the phone last saw it wins: the phone's change is dropped. Settings still to send count as unsent, so a background run sends them and sign-out keeps them.
- **Theme editor (T40 P1b, A416–A419).** Appearance → Duplicate makes an editable copy of a built-in theme and chooses it; Edit opens your own. The editor screen has a preview strip at the top, which is the editor page itself showing a sample note in its new `preview` mode, re-themed on each change. Below it are the name, Light and Dark, every colour in its group (a sheet with a saturation and brightness square, sliders, a hex field and the theme's own colours), the fonts and the note width; Duplicate and Delete are in the menu. Edits save after a short pause as `theme.custom.<id>`, offline too, through the settings queue, and the server merges them with edits made elsewhere since (A416, A417). The preview is never a second WebView: while a note's is still alive it waits, and a note opened while it is alive waits for it (A418). Contrast warnings below WCAG AA show beside each colour, from a Kotlin port of the web's checks; they advise, and the server's `parseTheme` decides what is valid (A419).
- **Trash (T40 P3a, A430–A434).** **Move to Trash** is in the note's ⋮ menu and in the sheet a long press opens in any list (with **Move to folder…**). The note leaves every list at once, offline too, with **Undo** for 5 seconds. The phone asks the server (`POST /api/notes/:id/trash`) once the note's own edits, and a move made here, have gone, so the server records the folder the phone had it in; it never sets the Yjs flag itself. Until the server's index agrees, a stale page cannot bring the note back, and Undo while the request travels, or after it got no answer, queues a restore rather than cancelling one the server may have. A restore made on another device that the phone had not seen wins over its move, and the phone says so, also when a background sync met it; no clock is compared. Only a 404 that says the note is gone drops the phone's copy. Home's ⋮ → **Trash** lists the notes in Trash on any device, with when each goes for good. **Restore** works offline and files the note back in its folder (the top level if it has gone). **Delete for good** needs the phone's admin sign-in, asks first, then BiometricPrompt. Moves to Trash and restores not sent yet count as unsent, so sign-out keeps them. When a note open on the phone is restored on the server and a conflict copy keeps what the phone had, the note says so, with **Open the copy**.
- **Keyboard, launcher and accessibility (T40 P9, A490–A499).** With a hardware keyboard, the web's shortcuts work on every screen with the user's synced bindings: in a note the editor page dispatches them (it sends app commands back to Kotlin), elsewhere `MainActivity.dispatchKeyEvent` hands Ctrl, Alt and F-key presses to one dispatcher that runs what the screen in front registered. Settings → Keyboard shortcuts lists, records, removes and resets them (synced as `keys.<id>`); Meta+/ shows Android's own list. A long press on the launcher icon offers Capture, New note, Today, Search and the two notes opened last; Home's ⋮ has Quick capture. Custom themes' text colours are moved to WCAG AA, screens do not slide with animations removed, and section titles are headings.
- **Comments (T48, D40, A770–A785).** A note's comment threads live in its own Yjs document, so the editor page reads and writes them, offline too, and Kotlin only shows what the page lists and asks it for each change, which then syncs as an ordinary edit (Kotlin never reads Yjs). The note's ⋮ menu has **Comments**, with the open count; the selection menu has **Comment** (a thread on the selection, or at the caret), and tapping a highlighted passage or a point's marker opens the sheet on that thread. The Comments sheet lists the threads in document order, orphans last, with the web's Open and Resolved filter: each thread's quote, its comments with their writers (agents marked ✦), its delivery to an agent session ("Waiting for …", "Sent to …", "Seen by …", "… replied", or "Not sent: …" when it failed, saying why), a reply field, Resolve or Reopen, **Send to…** (the server's `GET /api/agent-sessions?note=`, online only) and Delete. Ryan edits his own comments and removes any; removing an agent's is its undo (A779). A thread's first comment has its own Delete only while replies follow it: it is then marked removed, saying "Comment removed" with no actions, and the thread and its replies stay; the thread's Delete, which asks first, is the only way a thread goes (A784). The app tells the page who this phone is (`commentAuthor`: `device:` and the device's id, with `/api/me`'s name for it) when the page is ready and whenever the account changes, so its comments are written under this device's name and the server need not rewrite them (A781); until then they say "You". A comment is not an edit (A770): it leaves the offline index's text and Recent alone. A change to the comments alone moves the note in `/sync/changes` without counting as an edit (A783), so the open note's 10-second poll brings an agent's reply and its delivery state as they happen, and a background sync fetches one made elsewhere.

## Build (agent worker)

The worker has the toolchain: the Android SDK in `~/Android/sdk` (platform 37, build-tools 37.0.0) and Temurin JDK 21 in `~/opt/jdk-21`. The system Java 25 is a JRE without `javac`. The Taskfile defaults `ANDROID_HOME` and `JAVA_HOME` to those paths. Elsewhere, install Android Studio's SDK and a JDK 21, and set `ANDROID_HOME` and `JAVA_HOME` yourself.

```sh
task android:build     # editor page + debug APK
task android:test      # JVM + Robolectric tests, and the instrumentation APK compiled
task android:release   # signed App Bundle for Play (needs the signing settings below)
```

The debug APK is `apps/android/app/build/outputs/apk/debug/app-debug.apk`. It is about 40 MB, because the build is debug and unminified and Mermaid is bundled. CI's `android` job keeps the APK as an artifact (`penmoss-android-debug`) for seven days. It is never published: the Releases page has the public APK, the release build (next section).

`task android:apk:sideload` builds that public APK (P8, A1187): the release build type of `app.penmoss`, signed with the sideload key instead of Play's upload key, in `apps/android/app/build/outputs/apk/release/app-release.apk`. It needs `PENMOSS_SIDELOAD_KEYSTORE` (the `.jks` file, key alias `penmoss-sideload`) and `PENMOSS_SIDELOAD_PASSWORD` (the store's and the key's password), and takes `PENMOSS_VERSION_CODE` and `PENMOSS_VERSION_NAME`; without the key it stops and says so. `bash .github/scripts/apk-check.sh <apk>` checks one: `app.penmoss`, not debuggable, signed with APK Signature Scheme v2 or later by the sideload key's certificate alone (and, with `PENMOSS_VERSION_CODE` set, that version code). The Play bundle (`task android:release`) always keeps the upload key.

On the shared worker, run Gradle under the heavy-run lock and stop the daemon afterwards: `flock /tmp/penmoss-e2e.lock task android:test`, then `(cd apps/android && ./gradlew --stop)`. `gradle.properties` already caps the heap at 2 GB with two workers.

The app talks to no Penmoss server (T59): only to GitHub, for git notebooks and feedback. Debug builds also allow plain HTTP to `10.0.2.2` and `localhost`, for a fake GitHub in tests.

## Sideload Penmoss (the public APK)

Every APK on the Releases page is the **release build of `app.penmoss`** (P8, A1187), shown as "Penmoss": not debuggable, signed with one stable sideload key, and numbered by CI build (`versionCode` is the run number plus 1000, D65), so each installs over the one before with no uninstall.

1. On the phone, open [Releases](https://github.com/htxryan/penmoss/releases) in the browser and download the APK: `penmoss-<build>.apk` from a `build-<run>` release, or (from T80.6) `Penmoss.apk` from the `alpha` release or a stable one.
2. Open the download. The first time, Android asks to let the browser install apps: allow it, then go back.
3. Play Protect may say the developer is unknown: choose **More details → Install anyway**.
4. A newer APK installs over it the same way, and keeps the notebooks and settings.

**The signing certificate.** Every public APK is signed by this certificate alone, and CI fails a build signed by any other (`.github/scripts/apk-check.sh`). Its SHA-256 fingerprint, which penmoss.app shows beside the download:

```text
3D:B5:DA:CC:2F:A1:F5:DA:70:28:FA:78:A3:35:C8:3F:50:62:63:A5:15:88:15:B3:3C:EC:73:24:81:C3:DE:07
```

Check a downloaded APK with the Android build tools: `apksigner verify --print-certs Penmoss.apk` prints a line ending in `certificate SHA-256 digest: 3db5dacc…c3de07`: the same digits, in lower case, without colons.

**Before the first install:**

- **Penmoss from Google Play** (internal testing) is the same app id signed with Play's key, so Android refuses the APK over it ("App not installed"). Remove the Play install first; its notebooks need adding again.
- **The older debug builds** (`app.penmoss.debug`, "Penmoss (debug)", published before A1187) are a different app and stay installed beside it. Add your notebooks in the new app, then remove the debug one.

The key lives in the `android-sideload` environment as `PENMOSS_SIDELOAD_KEYSTORE_B64` and `PENMOSS_SIDELOAD_PASSWORD` (A405), and in Ryan's password manager. Losing it means every phone must uninstall before the next APK installs. That happened once: the first key was lost at the move to the public repository (D65), so the key changed on 8 Nov 2026 (A1219), and a phone with an APK from before then uninstalls Penmoss once and adds its notebooks again.

## Install a debug build on the Pixel

The debug app is `app.penmoss.debug`, shown as "Penmoss (debug)". It installs beside a Play build and beside the public APK, and is for development: it is debuggable and signed with the building machine's own debug key.

**With adb.** On the Pixel, turn on developer options (Settings → About phone → tap Build number 7 times), then turn on Settings → System → Developer options → USB debugging (or Wireless debugging). Then, from the Mac:

```sh
scp worker:src/penmoss-wt/t33-android-editor/apps/android/app/build/outputs/apk/debug/app-debug.apk .
adb install -r app-debug.apk
```

**Without a computer.** Put the APK where the phone can reach it (Google Drive, or email it to yourself), open it on the Pixel, and allow "Install unknown apps" when asked. Play Protect may warn about an unknown developer; choose **Install anyway**.

An APK built on another machine (or on a pull request's CI run) is signed with that machine's debug key. Switching between them needs an uninstall first (`adb uninstall app.penmoss.debug`).

## Run the device tests on the Pixel

CI runs all but the jank test on an emulator ([below](#the-instrumented-tests-in-ci-emulator-5580)). With the phone on adb:

```sh
cd apps/android && ./gradlew :app:connectedDebugAndroidTest
```

This runs two tests:

- `NoteListJankTest` flings through 5,000 notes and fails if more than 5% of frames are janky, which is the 60 fps check (A285).
- `TypingInstrumentedTest` holds the T2 spike's typing tests, run on the production editor. It types through the WebView's own `InputConnection`, composing then committing each word, and checks the note:
  - the T2 paragraph;
  - Enter and Backspace in a list made from the bar;
  - a bar button pressed mid-word;
  - Enter in the title;
  - a key-event baseline.

Unlock the phone and keep the screen on while they run.

## The software factory's proof on a slot's emulator (F8)

`task proof:android -- app.penmoss.editor.TypingInstrumentedTest[#method] …` is the factory's Android proof ([`factory.md`](factory.md)). It runs only inside a factory slot's sandbox, which sets the slot's AVD (`penmoss37-slot1` or `-slot2`, which the factory makes once in its own AVD folder from the API 37 image), its emulator port (5560 or 5562) and its own adb server port (5040 or 5041). So the two slots record at the same time without touching each other, or your own emulator.

It builds the debug and test APKs first, since a Gradle build beside a software-rendered emulator stops System UI responding. Then it boots the emulator headless (`-no-window -no-snapshot -gpu swiftshader_indirect -feature -Vulkan -crash-report-mode disabled`, F0.4) and waits up to 240 s for `sys.boot_completed` (`PENMOSS_EMULATOR_BOOT_SECONDS`). It turns animations off and lets the device settle: booted is not idle, and on a loaded Mac System UI can stop responding while the boot's broadcasts run, and its "isn't responding" dialog takes the input focus from the app (a test's typed keys land in the dialog). So it waits for the broadcasts to drain (`am wait-for-broadcast-idle`), then for the launcher to hold the focus with no dialog in front for 10 checks a second apart (`PENMOSS_EMULATOR_QUIET_SECONDS`), within 240 s (`PENMOSS_EMULATOR_SETTLE_SECONDS`; past that it says what has the focus and runs the tests anyway). Android closes the dialog itself once System UI responds. Error dialogs stay on: with `hide_error_dialogs` Android restarts a stalled System UI instead, and the new System UI's theme overlays change the configuration, which recreates the activity under test. It removes the last run's app, which another sandbox's debug key signed, and runs each named test under `screenrecord` (up to 170 s, `PENMOSS_PROOF_TEST_SECONDS`), with a screenshot after it; the screenshot comes after the test has closed its activity, so it shows what is left on screen, not the app. `apps/android/build/proof/` gets `report.json` and each test's `android-<n>.mp4`, `.png`, `.log` and `.logcat` (the device's log since the previous test, or since the boot for the first; it stays in the sandbox). The emulator shuts down when the script ends, fails or is stopped. A proof that runs past `timeouts.proofMinutes` (40) is stopped by the factory, which closes the sandbox and everything in it.

The PR's screenshot is the one the test takes itself: a proof spec calls `ProofShot.take()` (`app.penmoss.proof`, in `androidTest`) at its last assertion, while the change is on screen, and the script pulls `/sdcard/penmoss-proof.png` after the test. One taken after the test shows the launcher, since the app has closed; the script falls back to that, and says so, only when a spec took none (A1255).

To try it on slot 1: `task factory:doctor -- --full --only proof:android`. `tools/factory/test/android-proof.test.ts` checks the script against a stub adb and emulator.

## The instrumented tests in CI (emulator-5580)

CI's `android-emulator` job (A1227, [`ci.md`](ci.md) §1) runs the instrumented tests on every change `pick` counts as Android's, on a hosted Ubuntu runner with KVM (A1235): `:app:connectedDebugAndroidTest` on a headless emulator, with `.github/scripts/android-emulator.sh`. It is not a required check yet.

- **The emulator** is the AVD `penmoss37-ci`, made from the slots' API 37 image in its x86_64 build (`system-images;android-37.0;google_apis;x86_64`), which the runner's x86_64 CPU runs natively; the script takes the ABI from the machine, so on a Mac it uses the slots' own `arm64-v8a`. It boots with the proof's settings (`-no-window -no-audio -no-boot-anim -no-snapshot`, software rendering) after the APKs are built, and has 300 s to boot.
- **Its own ports:** console 5580 (`emulator-5580`) and adb's server on 5050, so on a Mac it never uses a slot's emulator (5560, 5562) or adb server (5040, 5041), or your own adb on 5037. One CI emulator runs on a machine at a time; a second waits for the first.
- **What runs:** every test in `app/src/androidTest` except `NoteListJankTest`, whose 60 fps check (A285) means something only on the Pixel. Run that one there, as above.
- **A failure** uploads `android-emulator-reports`: Gradle's HTML report, the JUnit XML and the emulator's log.

## Test the writing screen on the Pixel (T33)

1. **T2 protocol.** Re-run the T2 writing protocol in a note: Gboard typing, swipe typing, voice input, autocorrect and suggestions, the caret moved by long-press and by the space-bar drag, selection handles, and a paste. Note anything the editor got wrong.
2. **Long note.** Write a note of about 2,000 words over a few sittings. The caret should stay above the formatting bar, and nothing should need correcting that the editor caused.
3. **Formatting bar.** Try each button, with and without a selection. The keyboard should stay open, and pressed buttons should show what is on at the caret. Indent and outdent apply in lists; undo and redo apply to the phone's own edits.
4. **Back.** Type `/` or `[[`, then press Back: the menu closes and the note stays. Back again leaves. The predictive back preview shows when swiping from the edge with no menu open.
5. **Paste and pictures.**
   - Copy rich text from Chrome and plain text from another app, and paste both.
   - Paste a screenshot.
   - Add photos with the picture button, one of them a HEIC camera photo.
   - In airplane mode, add a picture and reopen the note: it shows. Turn the network back on and open the note on the web: the picture is there.
6. **Wikilinks.** Type `[[` and part of a title; pick a note, and pick **Create** for a new one (try it offline too). The new note uploads and lands in the same folder.
7. **Theme.** After deploying the server half, choose a theme and mode on the web (Settings → Appearance). Switch away from the app and back (a sync pass runs on return): the lists and the note follow it.
8. **Conflict copy.** On the phone, go offline and edit a note. On the web, restore an older version of it. Bring the phone online and open any note: a snackbar names the conflict copy. **Open** shows the phone's edits. Then try it while typing: with the note open and online, restore it on the web while you type, keep typing a few words, and leave the note. One copy should hold everything typed before the restore, including the last seconds.
9. **Device tests.** Run `./gradlew :app:connectedDebugAndroidTest` (above).

## Test capture on the Pixel (T34)

## Test background sync on the Pixel (T35)

Background sync needs no server change. Install the debug build and sign in first.

   1. On the phone, open Penmoss and let it sync, then leave the app (Home or another app; don't swipe it away).

2. **A restore while offline.** In airplane mode, edit a note on the phone. On the web, restore an older version of that note. Turn airplane mode off, wait a few minutes without opening Penmoss (or run the job as in step 1.5), then open it: Home says edits to 1 note could not sync. Open any note: the snackbar names the conflict copy, and the notice goes.
3. **Battery saver and Data Saver.** With battery saver on, or Data Saver on and Wi-Fi off, no background run syncs (step 1 does not bring the Mac's edits until you open the app). Opening the app still syncs.
4. **Mobile data.** With Wi-Fi off, make a new note on the Mac and edit one the phone already has. Leave the phone for an hour without opening Penmoss, then turn on airplane mode and open it: the edited note has the Mac's text, and the new note is listed but says it is not on the phone yet. Back on Wi-Fi, the next run (or opening the app) brings it.
5. **What WorkManager has scheduled.** With the phone on adb:

   ```sh
   adb shell dumpsys jobscheduler | grep -A12 app.penmoss.debug
   adb shell am broadcast -a androidx.work.diagnostics.REQUEST_DIAGNOSTICS -p app.penmoss.debug
   adb logcat -s WM-DiagnosticsWrkr
   ```

   The diagnostics list `penmoss.sync.periodic` (every hour) and, after the app was left with something unsent, `penmoss.sync.whenOnline`. Opening and leaving the app again does not re-issue the hourly job: its job id stays the same. To run the hourly work now: `adb shell cmd jobscheduler run -f app.penmoss.debug <job id from dumpsys>`.

### The 24 h idle battery test (A325)

1. Charge the phone, sign in to the debug build, open Penmoss once and let it sync, then leave the app.
2. Reset the battery statistics, then unplug the phone:

   ```sh
   adb shell dumpsys batterystats --reset
   ```

   Use wireless debugging for the later commands, or plug in only at the end: charging over USB stops the measurement.

3. Leave the phone idle for 24 hours: screen off, on Wi-Fi, no Penmoss use. Using other apps normally is fine, but note it. Edit a few notes on the Mac during the day, so some runs have something to fetch.
4. Collect the results without charging first:

   ```sh
   adb shell dumpsys batterystats --charged app.penmoss.debug > penmoss-battery.txt
   adb shell dumpsys jobscheduler | grep -A20 app.penmoss.debug > penmoss-jobs.txt
   adb bugreport penmoss-bugreport.zip
   ```

   Optionally load the bug report into Battery Historian (https://github.com/google/battery-historian) for a timeline.

5. **Passes when:**
   - Settings → Battery → Battery usage does not list Penmoss for the past 24 hours, or lists it under 1%;
   - `penmoss-jobs.txt` shows the app's job ran about hourly, or less often in Doze or once Android moves the unused app to a rarer standby bucket, and each run took seconds;
   - `penmoss-battery.txt` shows no wake lock for the app beyond WorkManager's own job locks, and a few minutes of mobile radio at most.
6. Optionally repeat one night on mobile data with Wi-Fi off: the same passes.

### Every release

1. **Build** on the worker, from an up-to-date main checkout:

   flock /tmp/penmoss-e2e.lock sh -c 'task android:release; r=$?; (cd apps/android && ./gradlew --stop) >/dev/null; exit $r'

   task android:publish-internal -- --dry-run

   The first validates an edit with the bundle on the internal track, then deletes it, so nothing is published; the second releases it to internal testing (status completed). ### Publish from the worker (once: a service account)

`task android:publish-internal` (`apps/android/play/publish_internal.py`, A692) signs in to the Google Play Developer API as a service account, with its JSON key at `~/.config/penmoss/play-service-account.json` on the worker. Until the key is there it stops and says so. Set it up once:

1. **A Cloud project and the API.** In the [Google Cloud console](https://console.cloud.google.com/), create a project (for example `penmoss-play`), then open APIs & Services → Library, find **Google Play Android Developer API** and choose **Enable**.
2. **A service account and its key.** In IAM & Admin → Service accounts, choose **Create service account** (name `penmoss-publish`), and grant it no Cloud roles. Open it → Keys → **Add key** → **Create new key** → **JSON**. The browser downloads the key: it is a password, so keep it out of chats, email and git, and keep a copy in the password manager.
3. **Invite it in Play Console.** In Play Console → Users and permissions, choose **Invite new users**, and enter the service account's email (`penmoss-publish@<project>.iam.gserviceaccount.com`, shown on its page). Under **App permissions**, add **Penmoss** with **Release apps to testing tracks** only, then **Invite user**. Play can take a few minutes to accept a new service account.
4. **Copy the key to the worker**, from the Mac (the download's file name differs):

   ```sh
   scp ~/Downloads/penmoss-play-0123456789ab.json worker:.config/penmoss/play-service-account.json
   ssh worker chmod 600 .config/penmoss/play-service-account.json
   ```

   Then delete the download. To check everything without publishing, build (above) and run `task android:publish-internal -- --dry-run` on the worker. A 403 means the invite (step 3) has not reached Play yet, or lacks Penmoss; a 404, the API is not enabled for the key's project (step 1).

The script never prints what the key holds. `--key <path>` or `PENMOSS_PLAY_KEY` names another key file, and `--aab <path>` another bundle; the track is always internal. Its tests use a fake Play client: `task android:publish:test`.
