# Software factory

The factory (#253, `tools/factory`) takes issues from Linear's **Penmoss** team (`PEN`) through planning, implementation and review on this Mac. Branches, pull requests, CI and merges stay on GitHub, and every CI job it waits on runs on the self-hosted Mac runners (A702).

The tracker is one line of `tools/factory/factory.config.json`: `"tracker": "linear"` (the default, A1221) or `"tracker": "github"`, which drives it from Project 8 as before. A GitHub App can't reach a project that belongs to a user, so switching back to Project 8 also needs a user's token for the board.

## Board

The card's status drives it:

| Status (Linear) | What happens                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Triage, Backlog | Nothing. The factory never touches these, and new GitHub issues land in Triage (D66).                                                                                                                                                      |
| Todo            | You move a card here to start it. The factory picks Todo cards by Linear's priority (Urgent first; no priority counts as Medium), then by the team's manual order.                                                                         |
| Planning        | The agent writes the plan (and a design artifact when the change affects what you see) and works through it with you in artifact comments, issue comments or a direct chat. Only your explicit yes ("complete", "agreed", "go") ends this. |
| In Progress     | The agent builds the agreed plan on a branch, validates it on each platform in scope and opens the PR.                                                                                                                                     |
| In Review       | The agent fixes failing checks and addresses each of your review comments in the same PR. When you approve, it merges and watches `main`.                                                                                                  |
| Done            | Set by the factory after `main` is verified.                                                                                                                                                                                               |
| Canceled        | Nothing.                                                                                                                                                                                                                                   |

On Project 8 (`"tracker": "github"`) the same steps are called Ready, Planning, In progress, In review and Done, and pickup order comes from the `P1`–`P4` labels, then board position.

**Blocked** is a label. While it is on a card, the factory does nothing with it: no picking, no replies, no pushes. The factory adds it when it is waiting on you; you can add it yourself to pause a card. Only you remove it; the factory has no code path that does. A card that Linear shows as **blocked by** an unfinished issue is held the same way, until that issue is done or canceled (LD8). On Project 8, Blocked is a single-select field instead.

The factory comments and moves cards as its own Linear app, the way its GitHub App opens its pull requests. Only your comments count as instructions; everyone else's, and the text of an issue that came in from GitHub, reach the agent fenced as untrusted (R14).

`task factory:next` prints the card the factory would start next and why, without changing anything. It names statuses and priorities as the tracker does: "the only card in Todo", "High", and "no priority (Medium)" for a card without one.

## Labels

| Label in Linear                                    | The factory reads it as                  | Meaning                                                                                          | When absent                                                                                                       |
| -------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `factory`                                          | the same                                 | The factory may act on the card at all (A1296); takes it through every status below              | Hands off: never planned, started, reviewed or merged, and a run in flight stops at its next step, as for Blocked |
| **Agent** group: `claude`, `opencode`              | `agent:claude`, `agent:opencode`         | Which agent CLI runs the issue                                                                   | `claude`                                                                                                          |
| **Model** group: `opus`, `sonnet`, `go`            | `model:opus`, `model:sonnet`, `model:go` | A model alias from `tools/factory/factory.config.json`; a model label alone also picks its agent | The agent's default (`opus`, `go`)                                                                                |
| `plan:skip`                                        | the same                                 | Skip planning and implement straight away                                                        | Plan first                                                                                                        |
| `platform:web`, `platform:mac`, `platform:android` | the same                                 | Narrows which platforms need proof (CI still tests everything the path classifier selects)       | The path classifier decides                                                                                       |
| `P1`–`P4` (Project 8 only)                         | the same                                 | Pickup order; on Linear, the issue's own priority does this                                      | P3                                                                                                                |

In Linear, the agent is a label in the group **Agent** and the model a label in the group **Model**, named without a prefix: `claude`, `opencode`, `opus`, `sonnet`, `go`. The factory reads a label in a group as `group:name` (`claude` in Agent is `agent:claude`, `go` in Model is `model:go`), and its messages and `task factory:next` name them that way. `plan:skip` and the `platform:*` labels are plain labels, in no group. A group holds one label per issue, so Linear itself refuses two agents. `task factory:linear:check` lists any that are missing, and `-- --fix` creates them. On Project 8 each label is named as the factory reads it.

Conflicting labels (two `agent:` or two `model:` labels, or `agent:claude` with `model:go`) stop the card from starting: the daemon says why on the issue and sets Blocked, and `task factory:next` says why too.

OpenCode runs under the same sandbox as Claude Code. Its permissions come from `tools/factory/agents/opencode.json`, whose bash deny list mirrors Claude's. The factory passes that file inline with the worktree's own OpenCode config turned off, so the agent can't loosen it.

File factory work with the team's **Task** template, which asks for acceptance criteria in EARS form. Its sections are Goal, Acceptance criteria, Automated checks, Manual checks, Depends on and Evidence. The factory doesn't require the template or its headings: the agent reads the whole description.

## Setup

Once, on this Mac:

0. **The checkout and the CLIs.** A checkout of `main` (`~/src/penmoss`) with Node 24 and `corepack pnpm install` done (`docs/development.md`), and `task`, `gh`, `claude` and, for `agent:opencode`, `opencode` on the PATH. Every `task factory:*` command runs from that checkout, whatever branch it is on. The daemon and the UI don't: `task factory:install` gives them a clone of their own (step 9), and the runs work in another clone under the state folder.
1. **The factory's GitHub App** (A1222). It pushes branches, opens and merges pull requests, and comments on them, as `penmoss-factory[bot]`. On GitHub, Settings, Developer settings, GitHub Apps, make a new app:
   - **Name** `penmoss-factory`. **Homepage** the repository's URL. **Webhook** off.
   - **Repository permissions:** Contents, Pull requests and Issues: Read and write. Actions, Checks, Commit statuses and Metadata: Read. Leave **Workflows** unset: GitHub then refuses any push from the factory that changes `.github/workflows`, so an agent can't change what runs on the Mac runners. A change there is yours to make. Nothing at the account level.
   - **Where can it be installed:** only on this account.

   Then **Install App** on `htxryan/penmoss` alone, and **Generate a private key**. Move the downloaded `.pem` to `~/.config/penmoss-factory/github-app.pem` and `chmod 600` it. Put the app's ID (on its settings page) and the key's path in `~/.config/penmoss-factory/github-app.env`, mode 600:

   ```
   GITHUB_APP_ID=123456
   GITHUB_APP_PRIVATE_KEY=~/.config/penmoss-factory/github-app.pem
   ```

   The key stays on the host. The factory makes an hour-long token from it for its own pushes and PRs, and a read-only one for each sandbox.

   GitHub takes PR attachments only from people, not apps, so the proof goes to Cloudflare R2 instead (A1223):

   - In the Penmoss Cloudflare account, create the R2 bucket `penmoss-factory-proof`. In its settings, under Public access, connect the custom domain `proof.penmoss.app`.
   - Under R2, Manage API tokens, create a token with **Object Read & Write** on that bucket only. Put its access key ID and secret, and the account ID, in `~/.config/penmoss-factory/proof.env`, mode 600:

     ```
     R2_ACCOUNT_ID=…
     R2_ACCESS_KEY_ID=…
     R2_SECRET_ACCESS_KEY=…
     ```

   The host uploads each run's screenshots and videos there and links them in the PR. Screenshots show inline; a video is a link to its MP4. Like the app's key, this file never reaches a sandbox.

2. **The factory's Linear app.** In Linear, Settings, API, make an OAuth application named **Penmoss Factory** with client credentials turned on. Put its client ID and secret in `~/.config/penmoss-factory/linear.env`, mode 600:

   ```
   LINEAR_CLIENT_ID=…
   LINEAR_CLIENT_SECRET=…
   ```

   The factory gets the app's token from them and acts as the app. This file is read on the host only. It is a different file from `factory.env`, so no sandbox ever sees it (LD4), and `task factory:doctor` checks that.

3. **Your own Linear key, for the Factory UI.** Make a personal API key in Linear (Settings, Security & access) and put it in your keychain: `security add-generic-password -s penmoss-factory-linear -a "$USER" -w`. The UI posts your replies and removes Blocked with it, as you. Nothing else reads it. To check it without reading the key, open the Factory UI: when the key is missing or doesn't answer as `linear.owner` (step 4), its header goes read-only and says why.
4. **The team.** `task factory:linear:check -- --me` prints your Linear user ID: put it in `tools/factory/factory.config.json` as `linear.owner`. Then `task factory:linear:check -- --fix` adds what the factory needs to the Penmoss team (the **Planning** state, the `Blocked`, `plan:skip` and `platform:*` labels, the Agent and Model groups), and `task factory:linear:check` should then pass.
5. **The env file.** `~/.config/penmoss-factory/factory.env`, mode 600 (`chmod 600`), with `KEY=value` lines. Paste each value into the file with an editor; never redirect a command's output to a file named after a token. Only these names reach a sandbox; any other line is ignored and named (never its value) by `task factory:doctor`:

   | Name                                            | What                                     |
   | ----------------------------------------------- | ---------------------------------------- |
   | `CLAUDE_CODE_OAUTH_TOKEN`                       | from `claude setup-token`                |
   | `OPENCODE_API_KEY`                              | the OpenCode Go key                      |
   | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` | a token limited to the Penmoss account   |
   | `PLAY_SERVICE_ACCOUNT_JSON`                     | the path of the Play service account key |

6. **The factory's claude.ai login.** Each agent session in a run gets a chat in the Claude app, which needs a claude.ai login (the setup token can't open Remote Control). Make a second login, for the factory alone, in its own config folder, signing in in the browser it opens: `mkdir -p ~/.config/penmoss-factory/claude && CLAUDE_CONFIG_DIR=~/.config/penmoss-factory/claude claude auth login`. It is `agents.claude.login` in `tools/factory/factory.config.json`. Claude Code keeps it in your login keychain, apart from your own login; the factory refreshes it and gives each session a copy of its short-lived access token only (Sandbox, A1287). `task factory:doctor` says when it expires (about a month after you log in) and warns in its last week: log in again the same way. Without it, sessions run on the setup token with no chat.
7. **Trust the planning folder.** Planning sessions run from `~/Library/Application Support/penmoss-factory/plans`. Make it and run `claude` there once, accepting the trust prompt, or `claude --bg` refuses to start: `mkdir -p ~/Library/Application\ Support/penmoss-factory/plans && cd "$_" && claude`. The trust is kept by path, so it survives the factory moving old plans to `archive/` when the tracker changes. `task factory:doctor` doesn't check this.
8. **Toolchain.** The JDK, Android SDK (with the API 37 image `system-images;android-37.0;google_apis;arm64-v8a`, from which the factory makes each slot's emulator itself) and Playwright's browsers at the paths in `tools/factory/factory.config.json` (`toolchain`), and the Tart test VM for Mac proof (`docs/ci.md` §8). Optional: `brew install terminal-notifier`, so a notification opens its card in the Factory UI.
9. **Check it.** `task factory:doctor` uses slot 1 even while the daemon runs, so run it when `task factory:status` shows that slot idle, or pass `-- --slot 2`. It runs with the PATH the LaunchAgents run with (not your shell's), checks that the host finds every command it runs there (`git`, `gh`, `node`, `corepack`, `claude`, `sandbox-exec`, `osascript`, `caffeinate`, `ffmpeg`, `tar`; a missing `terminal-notifier` or `opencode` is only a warning) and that the factory's claude.ai login is there and not about to expire (a warning otherwise), then starts slot 1's sandbox on a throwaway branch of `origin/main` and checks the toolchain there (pnpm, Chromium, the JDK, `wrangler dev` on the slot's port block), the tokens (the GitHub check uses the app's read-only token, as a run does, and GitHub must refuse it a branch with a 403 and a push; Claude Code and OpenCode each answer a one-word prompt, OpenCode with the `opencode` agent's default model and `OPENCODE_API_KEY`; and `opencode models opencode-go` must list every OpenCode model ID in `models`, so a renamed one shows up here rather than in a run; both OpenCode checks are skipped without the key), and that your gh login, `~/.ssh`, the keychain, the Mac app's data folder (its `git-secrets.json`), the GitHub App's key, the proof bucket's key, the Linear app's credentials and your home stay out of reach (each of those files is read for one byte, sent nowhere, and the check passes only when the sandbox refuses the read; a missing file or any other error fails it, A1258), and that a relay deploy and `task site:deploy` are refused. `-- --full` adds `task check` (every step of `check:all` and every package's tests, without stopping at the first failure, so all of the sandbox's failures show in one run), the e2e smoke spec, `task android:test`, one recorded instrumented test on the slot's emulator and `task desktop:build`; `-- --slot 2` checks the other slot, and `-- --base <ref>` branches from another ref than `origin/main`. The checks themselves come from the checkout you run it in: when that checkout's commit isn't on the base, the doctor says so, since a check added on a branch can't pass against code that isn't on the base yet.
10. **Start it.** `task factory:install` clones `main` into `~/Library/Application Support/penmoss-factory/code`, runs `pnpm install --frozen-lockfile` there for the factory alone, and installs the daemon and the UI as LaunchAgents that run from that clone (A1226). Both start now and at every login, and launchd starts either again, at most every 30 s, when it exits on an error (`KeepAlive` on an unsuccessful exit, `ThrottleInterval` 30); `task factory:stop` stops the daemon cleanly, and it stays stopped until `task factory:start`, which starts whichever of the daemon and the UI isn't running. The code they run, the prompts each run reads and `factory.config.json` change only when you run `task factory:update` (Daily use), never when you switch branches in `~/src/penmoss` or delete a worktree, so a change to `factory.config.json` takes effect once it is on `main` and you update. Run `task factory:install` again after a change to the plist template or to move to another Node; it leaves the clone at its commit.

## Daily use

1. **File an issue** in the Penmoss team with the **Task** template, label it `factory`, and move it to **Todo**. The factory acts only on cards with that label, so a card in Todo without it is left for you. Its priority sets the order; labels choose the agent, model and platforms, or skip planning (Labels, above).
2. **Planning.** The card moves to Planning, and the factory posts its session's chat link for the Claude app and the command that joins it from a terminal (`claude attach <id>`). When it has questions, it posts them on the issue and adds **Blocked**. Answer in the artifact comments, the chat, the issue or the Factory UI, then remove Blocked. Say **complete** when the plan is.
3. **Implementation** starts when a slot is free. The card moves to In Progress, the factory comments "Started: <agent> (<model>) on slot <n>…" on the issue, and `task factory:status` shows "running PEN-<n> on slot <n> since … (picked)". The run builds on its own branch, which starts from `main` as the factory has just fetched it (a restarted run's branch keeps its commits, rebased onto that `main` when they apply cleanly). It runs the gate (`task lint` or `task check`) once the branch is rebased onto `main` and its new decisions are numbered (Decision numbers, below), records proof, validates against the plan, rebases once more if `main` moved meanwhile (running the gate's check again only when that brought in more than `docs/decisions.md`; proof and validation stand), and opens a pull request whose body shows the proof from the R2 bucket when a platform is in scope. The body's text is the agent's and the reviewer's, with each new decision's number in place of its `A-NEW-n`; a risk that says a platform's spec couldn't run in the sandbox gets a note when the factory's proof ran it and it passed, and one only about the decisions table's padding or numbering is left out. The PR says `Part of PEN-<n>`, so Linear shows it on the issue without moving the card: the factory moves cards itself. Its title is the branch's first commit subject (or the summary's first sentence, at most 72 characters) and never names the card, since Linear's GitHub integration moves a card named in a PR's title. Keep card IDs out of your own PRs' titles too, unless the PR finishes the card. CI goes green in the same PR; a CI job the path classifier skips counts as passed. A red job whose log shows the runners' infrastructure failing (a name that doesn't resolve, a registry's 5xx, a runner that shut down; `INFRA_SIGNATURES` in `tools/factory/src/ci-failure.ts`) is re-run, at most twice per Actions run, rather than given to the agent, and the issue says so (A1312). A red job whose log names the tests that failed, when the branch changes none of them and the same job passed the last time main's CI ran it, looks like a flaky test: its failed jobs are re-run once per PR before the agent gets a repair round, and the issue says so (A-NEW-1). If `main` moved while CI ran, the run rebases onto it once more, runs the gate again and waits for CI again. Then the card moves to **In Review** and you get a notification. Each agent session in the run (the build, a validation, a fix round) posts its chat link for the Claude app on the issue as it starts, and the Factory UI shows it as **Open in Claude** while it runs: watch the agent there, or send it a message while it works. The chat ends when the session's turn does (Sandbox).
4. **Review.** Comment on the PR or request changes: the factory answers each comment in a new round on the same branch: in its thread for a line comment, and in the round's "Addressed in <commit>" comment for a PR comment or a review's summary. You can also push commits to the PR's branch yourself: the next round, repair or rebase builds on them and keeps them. A force-push that drops the factory's commits Blocks the card instead, since the factory never pushes over someone else's push (A1285). **Approve** to merge. The factory then squash-merges, watches `main`'s CI, says so on the issue and moves the card to Done. A job of that run that a newer merge's run cancelled (the Mac build and the releases share concurrency groups in `ci.yml`) isn't a failure: when nothing else failed, the factory waits for the newer run on `main` and judges by it (A1315). It deploys nothing: `main`'s CI publishes the APK and Mac builds, and production deploys (`task deploy` for the relay, `task site:deploy`) stay yours, run by hand (A1225).
5. **When `main` moves.** If GitHub says a PR in review no longer merges (it conflicts with `main`, or is behind it), the factory rebases it onto `main` in a fresh sandbox, runs the gate again, pushes and waits for CI, and says so on the PR. It does this before any CI repair or merge. When both sides only added rows to `docs/decisions.md`, as two factory PRs that each record a decision do, it keeps both, `main`'s first, and gives the PR's row a new number if `main` has taken its number. Any other conflict goes to the agent for one round; if that doesn't resolve it, the card gets **Blocked**, with the files named. If GitHub dismissed your approval when the rebase was pushed, approve again.

Whenever the factory needs you, it says why on the issue and adds **Blocked**. It never acts on a Blocked card. Add Blocked yourself to pause a card at any point: a run stops before its next step (a sandbox, the gate, a proof, a fix round, the push, the PR or the merge). A step already running, such as the gate's `task check`, finishes first, and the run's ledger and log say which step it stopped before. When you clear Blocked on an In Progress card, its run starts again on the same branch, says so on the issue, and updates its PR if it had opened one (R12). If its agent had already finished (the result it wrote, which the factory keeps in the run folder, and its commits on the branch), the run goes on from the gate instead of running the agent again.

`task factory:status` shows the commit the daemon runs (it logs it at startup too), what it is running and waiting on, and why a running card waits (the Mac proof waiting for the test VM, say). It warns when its LaunchAgent still runs from somewhere other than its own clone, and says when the daemon that wrote the status isn't running any more. `task factory:chat -- 41` prints PEN-41's planning chat link for the Claude app and joins the session in your terminal with `claude attach` (`-- 41 --print` only prints the link and the command). `task factory:logs` follows the daemon's log, `daemon.log` in the state folder (`~/Library/Application Support/penmoss-factory`). The UI's, `ui.log`, is beside it, and each run's agent log is `runs/<run>/agent.log` there; the daemon's log gives its full path as the run's agent starts. `task factory:run -- 36` runs PEN-36 now in the foreground on slot 1 (`-- 36 --slot 2` for the other), when it is in Todo or Planning, not Blocked, and labelled `plan:skip` or has an agreed plan.

**Updating the factory.** The factory updates itself: a third LaunchAgent, the updater (`app.penmoss.factory-updater`, log `updater.log`), looks at `origin/main` every `autoUpdateMinutes` (5) and, when main has changed `tools/factory/` or `scripts/vm/`, runs `task factory:update -- --wait` itself, then restarts on the new code. It updates nothing while the daemon is stopped, and doesn't retry a commit whose update failed (`auto-update.failed`); `autoUpdateMinutes: 0` turns it off (A1293). By hand, `task factory:update` moves the daemon's clone to the latest `origin/main`, runs `pnpm install --frozen-lockfile` again, rewrites both LaunchAgents and restarts them. While a run, review round or merge is active it refuses and names them. `task factory:update -- --wait` asks the daemon to start nothing new (no planning step, run, review round or merge) and waits for what is active to finish, then updates. If the install fails, the clone goes back to the commit it had and the LaunchAgents restart on that. Both LaunchAgents are running afterwards, even if you had stopped the daemon: it waits until launchd has really let go of the old ones before loading them again, and tries a load that fails (launchd's "5: Input/output error") again a few times. It ends by printing the new daemon's first status, waiting up to two poll intervals and a minute for it. Only the daemon prepares the runs' clone and the publish repo as it starts; the UI reads the tracker and the state folder only, so the two never write the clone's config at once.

`task factory:report` shows the last seven days' throughput (started, reached In Review, merged), gate and CI rounds per issue, time from claim to In Review, and the share of issues worked that a run left Blocked. `-- --from 2026-11-01 --to 2026-11-08` picks another range (local dates; `--to` is exclusive). It reads only the run ledger, `runs.jsonl` in the state folder (each run's events, and each merge's `merged` and `done`), never the tracker, so it counts the runs' own Blocked stops, not planning questions or a Blocked you set yourself, and after a change of `tracker` it covers only the runs since (the older ledger is in `archive/`).

## Troubleshooting

| What you see                                              | Do this                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A card stays in Todo                                      | `task factory:next` says why it isn't picked: labels, Blocked, blocked by another issue, closed, or no free slot.                                                                                                                                                                                                                                              |
| "Can't start" on startup                                  | The log names which: the GitHub App isn't installed on the repository or its key is for another app; `factory.env`, `github-app.env`, `proof.env`, `linear.env` or the key is missing or not mode 600; the Linear token is your own rather than the app's; or `task factory:linear:check` finds a gap.                                                         |
| "Linear's rate limit"                                     | The poll is skipped until Linear's reset time; cards aren't Blocked for it.                                                                                                                                                                                                                                                                                    |
| Old plans or runs went missing                            | Changing `tracker` moves the state kept by card number into `archive/` in the state folder, since GitHub #36 and PEN-36 are different cards.                                                                                                                                                                                                                   |
| A run Blocked on a usage limit                            | It waits for the reset by itself. Blocked after four limits in a row means the plan's quota is spent.                                                                                                                                                                                                                                                          |
| `factory:status` says the Mac proof waits for the test VM | Fix what it names (`docs/ci.md` §8): install `tart`, make the VM once with `task desktop:test:vm`, stop a VM started by hand (`tart stop penmoss-test`), or look at `test-results/vm/tart-run.log` in the run's worktree for a VM that won't boot. "Busy with another run" only means it is queued. The run carries on by itself; see Proof.                   |
| A run Blocked on "the Mac proof waited 12 h"              | The test VM stayed unusable for `macProof.waitHours`. Fix the reason the comment gives, then clear Blocked.                                                                                                                                                                                                                                                    |
| A run Blocked on "recording … proof took longer"          | The proof ran past `timeouts.proofMinutes` and was stopped with everything it started (Proof). Read the log the comment names, then clear Blocked.                                                                                                                                                                                                             |
| A card Blocked on "no longer rebases onto main"           | The comment names the files that conflict. Say on the issue how to resolve them, then clear Blocked: the factory rebases again, with your comment.                                                                                                                                                                                                             |
| A run Blocked on "the runners' infrastructure"            | GitHub's runners failed again after two re-runs (the comment names the signature). Re-run the jobs once GitHub recovers; when they pass, clear Blocked and the PR goes back to waiting on CI (A1312, A1298).                                                                                                                                                   |
| A run Blocked on "CI stayed red"                          | Read the failed job's log from the PR's checks, and fix it on the branch. Clearing Blocked alone gives the agent no more repair rounds: they're counted per PR (A1313). If it was a flake, re-run the job; once it is green, clearing Blocked sends the PR straight back to waiting on CI, with no new gate or proof (A1298).                                  |
| "CI waiting for a runner"                                 | The Mac runners (the budgets and main's builds, A1235) are busy or offline. They catch up on their own.                                                                                                                                                                                                                                                        |
| A planning session "idle without writing its state"       | Open its chat in the Claude app, or join it with `task factory:chat -- <n>`, and nudge it; or clear Blocked to resume it.                                                                                                                                                                                                                                      |
| "The run couldn't start the agent"                        | The factory can't find the agent's command (`claude`, `opencode`) on the PATH the comment gives, which is the LaunchAgent's. Install it there, or set its full path as the agent's `bin` in `tools/factory/factory.config.json` and run `task factory:install`, then clear Blocked. The card itself is fine.                                                   |
| What the agent did in a run                               | The run folder (`~/Library/Application Support/penmoss-factory/runs/<run>/`) has `agent.log`, Sandcastle's rendering (its closing "without completion signal" line is expected: the factory reads `.factory/result.json` instead), and `agent.stream.jsonl`, the agent's raw stream, whose first line is its init event (the tools and MCP servers it loaded). |
| A sandbox check fails                                     | `task factory:doctor -- --full --only "<check>"`; the full log is in `~/Library/Application Support/penmoss-factory/doctor/`.                                                                                                                                                                                                                                  |
| "runs from …, not the factory's own checkout"             | The LaunchAgents predate the factory's own clone (A1226): run `task factory:install` once, then `task factory:update` from then on.                                                                                                                                                                                                                            |
| "Not updating: the daemon is busy"                        | A run or merge is active. Wait, or `task factory:update -- --wait`. Stopping the daemon (`task factory:stop`) and then updating works too: R12 restarts the runs on their branches.                                                                                                                                                                            |
| "Not updating: the daemon has not polled"                 | The daemon holds its lock but didn't poll within three intervals. Read `task factory:logs`; `task factory:stop`, then update.                                                                                                                                                                                                                                  |
| "Update failed"                                           | The fetch or the install failed, and the daemon restarted on the commit it had. Fix the cause (often the network, or a lockfile out of date on `main`) and update again.                                                                                                                                                                                       |
| "The new daemon hasn't reported"                          | The update restarted the LaunchAgents, but the daemon wrote no status within two poll intervals and a minute. Read `task factory:logs`: a daemon that exits on an error is started again within 30 s; `task factory:start` starts it now.                                                                                                                      |
| "launchctl bootstrap … failed 4 times"                    | launchd kept refusing to load that agent. `task factory:start` tries again; if it still fails, log out and in, then `task factory:start`.                                                                                                                                                                                                                      |
| Disk filling up                                           | The janitor removes old sandbox worktrees and run folders every six hours. To clean now, restart the daemon (`task factory:stop`, then `task factory:start`, which loads its LaunchAgent again).                                                                                                                                                               |

Besides the agent's log, a run folder keeps what each step left once its sandbox closed: `result.json` (the agent's last result), `gate.log` (the gate's whole check output, when it failed), `proof-<platform>.log` (each web and Android proof's output), `raw/` (the proof's videos and screenshots) and `validation/<n>/` (each validation's review, captures and image pairs). Every `task factory:*` command prints its usage with `-- --help` (or `-h`) without doing anything, `factory:stop` and the other shell-only tasks included (A1272).

## Turning it off

- **Pause one card:** add Blocked.
- **Pause everything:** `task factory:stop`. Runs in progress stop. They restart on the same branch when the daemon starts again (R12).
- **Remove it:** `task factory:stop`, then `launchctl bootout gui/$(id -u)/app.penmoss.factory-ui`, and delete `~/Library/LaunchAgents/app.penmoss.factory*.plist`. Then delete `~/Library/Application Support/penmoss-factory` (the factory's own clone is in it too) and `~/.config/penmoss-factory`. Also delete the `penmoss-factory` GitHub App (or uninstall it from the repository), and the Penmoss Factory app in Linear's settings.

## Sandbox

Every run is Sandcastle's Seatbelt sandbox (`tools/factory/src/sandbox.ts`). It sees its worktree, the JDK, Android SDK and Playwright's browsers (read-only), a pnpm store, Gradle home and AVD folder the factory owns under `~/Library/Application Support/penmoss-factory`, the slot's port block (`scripts/ports.mjs`) and emulator, and the env file's tokens. It doesn't see your home, logins or caches. Four rules beyond Sandcastle's profile (Chromium's Mach rendezvous service; the `hw.` and `machdep.cpu.` sysctls the emulator reads; `kern.boottime`; and the `sysctl` command's name lookups), a longer worktree timeout, and the agent log's absolute path in the line each agent starts with, are carried as a pnpm patch in `tools/factory/patches/`. A run sets `PENMOSS_FACTORY_RUN=1`, and the relay's deploy script refuses to run under it: production deploys happen after you merge (FD24). The Mac's heavy-job slots (W12) stay outside the sandbox: the factory takes one on the host around its gate, proof and the doctor's slow checks, and each sandbox has a one-slot folder of its own (A1216).

**Chat with a run's agent (A1287).** `claude -p` can't open Remote Control, so with the factory's login (Setup step 6) each Claude session runs as an interactive `claude --remote-control "[PF] Penmoss PEN-<n> run"` under a small runner in the sandbox (`tools/factory/sandbox/remote-claude.ts`, mounted read-only). The runner gives Claude a terminal, passes the prompt, and turns the session's transcript into the stream Sandcastle reads, so `agent.log`, `agent.stream.jsonl` and usage-limit waits work as before. Hooks end the session when its turn ends; the agent can't ask a question or wait on a plan's approval. A turn that ends while a command the agent started in the background still runs isn't the end: the command's notification starts the next turn, and the session ends with that one, or 30 minutes after, if the notification never comes (A1295). Before each session the host refreshes the login if its access token has under 4 hours left (`claude auth login` with the refresh token: Claude Code's own refresh), then copies the access token alone, never the refresh token, into `claude-login/slot<n>` in the state folder, which only that slot's sandbox reads, and deletes it when the session ends. The agent can read that token while it runs, as it can the env file's; it lasts about 8 hours. A login that is missing or can't be refreshed only costs the chat: the session runs on the setup token, and its run log says why. Whatever a session leaves running in its worktree (a dev server, a test run) is stopped when its sandbox closes, and before the next one opens, so it can't hold the run's ports (A1297).

**A ready sandbox (A1289).** Before the agent starts, the host installs the workspace's dependencies in the sandbox from the factory's pnpm store (frozen and offline, a few seconds) and writes a `.zshenv` in its home, so here-documents work (zsh's temp files go to the sandbox's `$TMPDIR`, not `/tmp`) and Gradle has Java's temp folder and home in the sandbox without the agent exporting them. The agent runs `task check:changed -- origin/main` and its e2e specs before it finishes; the gate runs the whole `task check`.

**GitHub from the sandbox.** An agent can't push, comment or merge. Its deny rules refuse `git push`, the clone's push URL is a dead end, and its `GH_TOKEN` is the GitHub App's read-only installation token (contents, metadata, pull requests, checks and actions, read; A1222), so GitHub refuses a push even to an explicit HTTPS URL (`task factory:doctor` checks that). Pushes, PRs and merges come from the host with the app's write token, after the gate passes. A ruleset on `main` that requires a pull request (Ryan's call) keeps even that token off `main`. The app's key, the proof bucket's key and the Linear app's credentials never enter a sandbox (`task factory:doctor` checks all three). (This replaces FD23's known gap, which came from the bot account's token.)

**Git on the host.** The host never runs git in the runs' clone (`<stateDir>/repo`) or a sandbox's worktree: a sandbox can write the top of that clone's `.git`, and a `commondir` there points git at a config of the agent's choosing (URL rewrites, push URLs, proxies). To read or publish a run, the host fetches its branch _from_ the clone into the publish repo (`<stateDir>/publish`: bare, mounted by no sandbox, with config only the host writes), refuses it unless it descends from the main the run was rebased onto, and diffs, reads and pushes there with the app's write token. Each sandbox fetches main into the clone itself as it starts, with its read-only token, and puts it at the main the host fetched into the publish repo for the run; a branch with no commits of its own (a new one, which Sandcastle makes from the clone's main) is moved onto that commit (A1232), and one with commits (a restarted run's, or a fix or review round's) is rebased onto it when its tracked files are clean and the rebase goes through; otherwise it stays where it is, for the gate's rebase. The gate sandbox fetches main and puts it there again before each rebase, and the planning snapshot is main's files exported from the publish repo. Every host git command runs without your git config (`GIT_CONFIG_GLOBAL=/dev/null`, no system config, no prompts) and with hooks, fsmonitor, credential helpers, the file transport for submodules and submodule recursion turned off (`tools/factory/src/git.ts`). The janitor runs no git: it deletes only folders directly in the clone's `.sandcastle/worktrees`, never a path that `git worktree list` names. The Mac proof runs the factory's own copy of the VM script, never the worktree's, with the worktree in `PENMOSS_VM_ROOT` (A1230).

**The issue's images.** Linear serves the images in an issue from `uploads.linear.app`, which needs the factory app's token, and no agent gets that. So before a planning session or a run's agent (a build, review, rebase or CI round) gets the issue, the host downloads each image in the description and in your comments with the app's own client, and the issue's text points at the local file, with a list of them after it. It takes at most 10 images, each up to 10 MB, and only PNG, JPEG, GIF and WebP. A planning session reads them from `plans/<n>/attachments`, which only the host writes; a run's agent reads them at `.factory/attachments/` in its worktree, copied there from the run folder (`runs/<run>/attachments`) as each sandbox opens. The token goes to `uploads.linear.app` alone, never to a server it redirects to. An image that fails to download, or is past the limits, is named in the text with the reason, and the run goes on without it. Others' comments stay data (R14): their images aren't downloaded (A1261).

**Prompts and main.** In a sandbox, main is `origin/main`, put where the host fetched it; the clone's local `main` is stale. The build, gate-feedback and rebase prompts say so and name `origin/main`. The build prompt also states the path classifier's rules (Proof), so the agent plans a proof spec for every platform the gate will want before it starts (A1254).

**Proof output.** Each proof's whole output (web, Android, and the Mac VM's `desktop-test.log`) is kept in the run folder as `proof-<platform>.log`, because the gate's worktree is gone once it closes. When a platform's proof specs don't pass, the agent's feedback includes that output's error lines and last lines (A1252, A1291), and its next sandbox has each proof's last screenshot in `.factory/last-proof/`.

**The gate's dependencies.** After the rebase and the decision numbers, the gate runs `pnpm install --frozen-lockfile --prefer-offline` in its checkout, then the check. The rebase can bring in main's changed lockfile, and without the install the check ran on modules the agent installed for the old one (A1251). A failed install goes back to the agent like a failed check.

**Workflows.** The gate refuses a branch whose diff against `origin/main` touches `.github/workflows/`, before the check and before any push, and tells the agent to put it back (A1314): the factory's GitHub App has no workflows permission (Setup, above), so GitHub would refuse the push anyway, late. The build and CI repair prompts say so too, and that a failure in the runner's network or a hosted service isn't the branch's to fix: the agent changes nothing and reports `failed` with the log lines. A workflow change is yours to make.

**Decision numbers.** An agent records a decision as a new row `| A-NEW-n |` in `docs/decisions.md`, and the factory gives it a real number after the gate's rebase, before the gate runs: the next one after `main`'s highest and the highest it has already given out (the `decision-numbers` file in the state folder, so two slots never take the same one). It reads what the branch added in the publish repo (`git diff` from the run's base) and numbers only that: a placeholder is defined by a row the branch added, and gets its number in that row and in the branch's other added lines that name it, outside `tools/factory/`. A placeholder in text the branch didn't add, such as the instructions in `AGENTS.md` and the prompts, or one the branch never defined, stays as it is. The numbers go in one more commit; a branch with no new decision gets no commit and reserves nothing (A1232). A number `main` takes meanwhile is moved on after a later rebase (A1228). Then it formats `docs/decisions.md` with Prettier, using its own settings, since a number is narrower than the placeholder an agent's Prettier padded the table for. A decision added by hand takes its number from the same counter: `task decision:next` (`-- --count 2` for two) reserves the next number after `origin/main`'s, your checkout's and every one the factory has given out, and prints it, so an open run and your PR never both take it (A1253). Inside a factory run it refuses: agents write `A-NEW-n`. When main has gained a decision since the branch's base, the gate's rebase merges `docs/decisions.md` itself, also when the branch's Prettier re-padded the whole table: it merges the three versions with each cell's padding taken out, then formats the result (A1250). The factory's own numbering commit is replayed rather than merged: it numbers the branch's rows that main doesn't have on top of main's table, so a decision merged to main mid-run, by hand or by another run, costs the agent no round (A1292). Any other commit that still conflicts there, such as an agent's later edit of its numbered row beside main's new one, has its row changes applied to main's table by row ID, with the padding ignored, then the table is formatted (A-NEW-1). An edit of the same row on both sides still goes to the agent. When the gate's check fails, the run folder keeps its whole output as `gate.log`, and the feedback shows the error lines, then the last 30. Each `gate-failed` event in `runs.jsonl` and `daemon.log` says why in one line (`reason`: `task check failed`, `rebase conflict: docs/decisions.md`, `mac proof: 1 failed (…)`), and a gate run again after a rebase logs `gate-passed` with `phase: rebase` when it passes.

**The Release note (PEN-105, A1300).** Every PR the factory opens carries a `## Release note` section, which the Release note check reads and the release jobs collect. The agent writes it as `releaseNote` in `.factory/result.json`: one line per user-facing change, or `none`. The run checks it with the same parser as the check (`.github/scripts/release-note.mjs`) before the gate. A missing or malformed note sends the agent back once, with the parser's errors and its work left as it is. If the note is still wrong after that, the run sets Blocked and says why on the issue.

## Proof

After the gate passes, the harness records each in-scope platform's proof specs itself (`.factory/result.json` names them), holding one of the Mac's heavy-job slots. Each platform's recording has `timeouts.proofMinutes` (40). At the timeout the factory stops what the proof started, not only the wait for it: a command it runs on the host gets its own process group, which gets SIGTERM, then SIGKILL a grace later, and so does the group if the daemon itself dies mid-proof (`tools/factory/src/exec.ts`).

- **Mac** runs in the test VM (`scripts/vm/desktop-test.sh`, `docs/ci.md` §8), which only the host can start. The host runs the factory's own copy of the script, which copies the run's worktree (`PENMOSS_VM_ROOT`) into the VM. Before it, the factory asks the script's `--check` whether the VM can take a run now. While it can't (`tart` missing, the VM `macProof.vm` not made, another run on it, a VM started by hand, or a boot that didn't answer: the script's exit 75), the run waits without failing or using a gate round, asks again every poll, and `task factory:status` shows the reason. The waits hold no heavy-job slot. After `macProof.waitHours` (12) it stops, Blocked, with the reason. At the proof timeout the script is stopped with its `tart run`; its trap stops the VM, which frees the VM's lock for the next run.
- **Android** runs on the slot's own emulator, in its sandbox. `am instrument -w` has no timeout of its own and waits as long as a hung test does, so at the proof timeout the host stops the slot's emulator, which ends it, and closing the sandbox ends the rest. Before each Android proof the host also stops an emulator a stopped run left on the slot's port and removes the AVD's stale lock files, so the next boot isn't refused.

A proof is what you watch, so each spec brings the change on screen, holds it about two seconds and ends on it: the window is 1280×720, and the web and Mac proofs' screenshot is taken when the spec ends, so a change below the fold has to be scrolled into view. An Android instrumented test calls `ProofShot.take()` (`app.penmoss.proof`, in `androidTest`) at its last assertion, and `proof.sh` uses that screenshot: one taken after the test shows the launcher, since the app has closed by then. A spec that takes none gets the screen after the test, and the proof's log says so (A1255). The Android video ends half a second after that screenshot (A1279). The build prompt asks for all of this.

**Proof carried over.** When a run's proof passes, and its validation when one runs, the run folder keeps `proven.json`: the proof, the reviewer's verdicts and a print of the branch's own diff against main without `docs/decisions.md` (`tools/factory/src/carry.ts`). A later run of the same card whose gate finds the same print, such as a recovered run that rebased past another PR's decision row, doesn't record the proof or run validation again: it reuses that run's, with the same proof specs and plan, logs `proof-reused` and `validation-reused`, and the PR links that run's files and says the proof was carried over from it. Any other change, or anything missing, and the proof and validation run as usual.

## Planning

A Todo card (Ready on Project 8) without `plan:skip` moves to Planning. Planning doesn't take a slot. The daemon starts one background Claude session for the card (`claude --bg --name "[PF] Penmoss PEN-41 plan" --remote-control "[PF] Penmoss PEN-41 plan"`, named after the card as the active tracker numbers it; every session the factory starts begins with `[PF] `, so the Claude app tells them apart from yours, A1288). The session reads a snapshot of `main` and the issue's images (Sandbox), can write only to its own output folder, and has no MCP servers and no Chrome. It publishes the plan, plus a design if what users see changes, as artifacts. Its prompt says how the gate proves each platform (Proof), so a plan asks only questions that have more than one answer (A1262). The session runs on your own Claude.ai login (the `claude` signed in on this Mac), never the factory's setup token, which can only make model requests and can't open Remote Control. Implementation runs sign in with the factory's own claude.ai login instead (Sandbox, A1287). So there are two ways to chat with it. In the Claude app, on the Mac, on claude.ai or on your phone: `claude --bg` doesn't print the link, so the factory reads the session's Remote Control id from Claude Code's job file (`~/.claude/jobs/<id>/state.json`, `bridgeSessionId`) for up to 20 seconds after it starts (A1257). And from a terminal on this Mac, in your own Claude Code: `task factory:chat -- <n>` prints the link and runs `claude attach <id>` for the card's current session (Ctrl+Z returns to your shell; the session keeps running). The issue's comments and the Factory UI give both. Each resume starts a new session, with a new id and a new link, and the daemon posts the new link on the issue (A1281, A1286). On every poll the daemon reads the session's `state.json`:

- **Waiting on you.** The daemon posts the open points with the links, sets Blocked and stops the session. Questions with a few clear answers list them, so you can pick one in the Factory UI. Answer in the artifact comments, the chat or on the issue, then clear Blocked. The session resumes with your issue comments and checks the artifact for the rest. Anyone else's new comments go along fenced as untrusted data (R14): they never resume the session or end planning.
- **Agreed.** Only an explicit yes ("complete", "agreed", "go") counts; "looks good, but…" is feedback. A yes as an issue comment counts too. When the session reports a yes on the issue, the daemon checks your own comment there holds the words it quotes; if none does, it asks you instead. The daemon keeps a copy of `plan.html` that later edits can't change and stops the session. The card implements next, with that plan in the prompt, ahead of new Todo cards.
- **Trivial.** The session may judge an issue too small to plan (`planning.agentMaySkipTrivial`). The daemon says why on the issue and implements it.
- **Quiet.** If the session is idle for 10 minutes without writing its state, the daemon says so and sets Blocked.

The daemon never acts on a card while Blocked is set, not even on a yes.

## Validation

When a planned change reaches an app (the web, the Mac or Android), the gate and proof run first, then validation. Before it starts, the host renders each agreed mockup to `.factory/validation/<id>-mockup.png` in the gate's sandbox, with the repository's Playwright in headless Chromium: at 1280×800, or 390×844 when the page's content is no wider than a phone (`sandbox/render-mockups.cjs`). One agent session then walks each acceptance criterion on the app it is about, one criterion per Playwright test with a 20-second timeout, and screenshots it at its mockup's size; it renders only a mockup the host couldn't (A1323). It walks the web build itself, in headless Chromium on the slot's port block. It can't run the Mac app or the emulator, so for those it writes a walkthrough: a Playwright-for-Electron spec, `apps/desktop/test/e2e/factory-walk.spec.ts`, saving `test-results/walk/<id>-mac.png`, and an instrumented test, `app.penmoss.walk.FactoryWalkInstrumentedTest`, calling `ProofShot.capture("<id>-android")`. After the session the host runs them where the apps run: the Mac one in the test VM, waiting for it as a Mac proof does, the Android one on the slot's own emulator through `proof.sh`. Their screenshots join the web ones in `.factory/validation/`, and each one's log is kept in the run folder (`walk-mac.log`, `walk-android.log`). A walkthrough that couldn't run, or failed, never stops validation: the reviewer is told why, and records the rows it couldn't capture as deviations (A1280). A second, independent session compares each pair and gives a verdict: match, mismatch or deviation. It also reads what the builder said it couldn't do and why (`risks` in `.factory/result.json`), so a reason that holds becomes a deviation with that reason. A mismatch goes back to the builder, using the gate's fix rounds. Whatever is still wrong after the last round goes in the PR as a deviation. The PR shows a fidelity table with each mockup beside its screenshot. Each validation's files (`review.json`, `captures.json` and every screenshot and mockup pair) are kept in the run folder, in `validation/1/`, `validation/2/`… one per round, since the gate's worktree is gone once it closes. Each row says where its screenshot comes from: "Mac app, in the test VM" or "Android app, on the factory's emulator" over a walkthrough's screenshot. A row about the Mac or Android app that only the web build captured (that app wasn't in the change's scope) says it shows the web build standing in for it (A1256).

## Factory UI

`task factory:install` also starts the UI at login: a page on `127.0.0.1:7878` (`task factory:ui:open`; `task factory:ui` serves it in the foreground when its LaunchAgent isn't running). It updates itself every few seconds and has two views, switched in its header (A1233, A1265):

- **Inbox:** what needs you, oldest first, then what the factory is working on (only when it is) and the queue in pickup order. Each card is its key and title and one line saying what it needs, such as "Answer 4 questions on the plan", "Review PR #85" or why it stopped, with how long it has waited; its colour is the edge beside it. The card you pick (the oldest, until you pick another) opens beside the list.
- **Pipeline:** a row per card and a column per step (Todo, Plan, Build, Gate, Proof, PR + CI, Review, Merge, Done), with a coloured marker on the card's step: blue while the factory works, amber when it's your turn, red when it stopped, purple when it won't start, grey when queued or paused (the legend above the board says so). Clicking a row opens the same detail as the Inbox. Under the board, **Activity** shows the slots' runs over the last 12 hours and what happened, newest first, with a card's repeats folded into one line ("Blocked ×4, 08:12–10:08"). Every run on the timeline shows its card's full key: inside its chip when the chip is wide enough, else beside a chip drawn at the run's true length, and a run that would cover another on its slot takes a further row (A1284).

The detail, top to bottom: the card's key and title; one line of its status, agent and model, size and slot; its links as buttons (the issue, the plan and design artifacts, the pull request and CI); the steps; then **Your turn**: what is asked, what to do about it (a run that failed before the agent started says so, with the error and the command that fixes it), a planning card's chat (**Open in Claude**, its link in the Claude app, beside the command that joins it from a terminal), the planning questions, and the reply box. The live run's agent log and the card's runs, with the run folder's path, are folded below.

Only the factory's own cards are shown: Todo and Planning cards, and In Progress, In Review or Done cards whose claim is in the run ledger (`runs.jsonl`). An In Progress card the factory never claimed, such as a task you're doing yourself, is counted under **Not in the factory (n)**, folded, not listed. A card you set Blocked on yourself is paused, in the queue, not in Needs you.

The header holds one health pill: "Running · 1 of 2 slots busy" when all is well, amber when something needs fixing (a daemon running from the wrong checkout, a failing doctor check), red when the daemon's pid has exited or it hasn't polled for three intervals. Click it for the daemon's pid, its commit, when it last polled, its slots and the doctor's last result. When something is wrong a banner under the header also says so, with the command to run, and when the daemon isn't fresh the rest of the page is dimmed: it is as of the last poll. At phone width it's one column with a header of two lines, and a notification's link opens on its card.

The page is light by default, whatever your OS uses. The toggle at the right of the header picks Light, Dark or System (which follows the OS); each browser remembers its choice.

From the page you can also reply on an issue (and clear Blocked in the same click), answer the plan, say **Complete** to agree the plan, and set or clear Blocked. Each planning question shows the planner's proposal under it and its options as buttons, the proposed one marked; pick an answer for each, add anything else in the reply, and **Send answers and continue** posts them as one comment and clears Blocked, so the session resumes with every answer at once. Each card has one main button for what it needs (**Send answers and continue**, **Post and retry** or **Post**); the others are quieter. These writes use your own Linear key from the keychain item `penmoss-factory-linear` (Setup, step 3), never the factory app's, so they appear as yours. Without that key, or when it doesn't answer as `linear.owner`, the page is read-only: it says why, and its buttons stay off. On Project 8 the writes use your own `gh` login instead, and the page is read-only unless it is signed in as `htxryan`. A card that Linear holds only because an unfinished **blocked by** issue waits in the queue and names that issue; it has no Blocked to clear, but you can still set Blocked on it. The daemon can set Blocked but has no code that clears it; a test keeps the UI's writer out of the daemon.

The token is kept in the state folder (`ui-token`, mode 600), so the link stays the same across restarts and updates; delete that file and restart the UI for a new one (A1264). It keeps anything else on this Mac that can reach the UI's port, a factory agent among them, from pressing your buttons: Tailscale decides which devices reach the Mac, not which programs on it reach the UI. The link carries it once, as `?token=`, which sets the cookie `penmoss-factory-ui`; the cookie then carries it for a year, including when you tap the link in another app (A1249). The current local link is in `ui.url` in the state folder and in `ui.log`, and `task factory:ui:open` opens it in a browser. For scripts, `/view.json` returns the page's state as JSON (send the cookie). Requests without it, from another `Origin` or for another `Host` get 403. The UI listens on no other interface. To open it on your phone or another of your devices, run `task factory:ui:tailnet` once: Tailscale serves it on your tailnet at `https://<this Mac>.<tailnet>.ts.net:8443` (never Funnel, so never the internet), and the UI accepts that name too; `ui.log` gives the link with its token (A1246). `tailscale serve --https=8443 off` turns it off. With [`terminal-notifier`](https://github.com/julienXX/terminal-notifier) installed (`brew install terminal-notifier`), clicking a factory notification opens its card.

There is no pause button for the whole factory yet: pause one card with Blocked, or stop the daemon (Turning it off). The page shows a run's folder as a path to copy rather than revealing it in Finder.

The page's own check runs headless Chromium against a fake state folder: `pnpm --filter @penmoss/factory e2e` (A1234). It never opens a window on the Mac.
