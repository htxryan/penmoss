# Software factory

The factory (#253, `tools/factory`) takes issues from Linear's **Penmoss** team (`PEN`) through planning, implementation and review on this Mac. Branches, pull requests, CI and merges stay on GitHub, and every CI job it waits on runs on the self-hosted Mac runners (A702).

The tracker is one line of `tools/factory/factory.config.json`: `"tracker": "linear"` (the default, A1221) or `"tracker": "github"`, which drives it from Project 8 as before. A GitHub App can't reach a project that belongs to a user, so switching back to Project 8 also needs a user's token for the board.

## Board

The card's status drives it:

| Status (Linear) | What happens                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Triage, Backlog | Nothing. The factory never touches these, and new GitHub issues land in Triage (D66).                                                                                                                                                      |
| Todo            | You move a card here to start it. The factory picks Todo cards by Linear's priority (Urgent first; no priority counts as Medium), then by the team's manual order.                                                                         |
| Planning        | The agent writes the plan (and a design artifact when the change affects what you see) and works through it with you in artifact comments, issue comments or a direct chat. Only your explicit yes ("complete", "agreed", "go") ends this. |
| In Progress     | The agent builds the agreed plan on a branch, validates it on each platform in scope and opens the PR.                                                                                                                                     |
| In Review       | The agent fixes failing checks and addresses each of your review comments in the same PR. When you approve, it merges and watches `main`.                                                                                                  |
| Done            | Set by the factory after `main` is verified.                                                                                                                                                                                               |
| Canceled        | Nothing.                                                                                                                                                                                                                                   |

On Project 8 (`"tracker": "github"`) the same steps are called Ready, Planning, In progress, In review and Done, and pickup order comes from the `P1`–`P4` labels, then board position.

**Blocked** is a label. While it is on a card, the factory does nothing with it: no picking, no replies, no pushes. The factory adds it when it is waiting on you; you can add it yourself to pause a card. Only you remove it; the factory has no code path that does. A card that Linear shows as **blocked by** an unfinished issue is held the same way, until that issue is done or canceled (LD8). On Project 8, Blocked is a single-select field instead.

The factory comments and moves cards as its own Linear app, the way its GitHub App opens its pull requests. Only your comments count as instructions; everyone else's, and the text of an issue that came in from GitHub, reach the agent fenced as untrusted (R14).

`task factory:next` prints the card the factory would start next and why, without changing anything. It names statuses and priorities as the tracker does: "the only card in Todo", "High", and "no priority (Medium)" for a card without one.

## Labels

| Label                                              | Meaning                                                                                          | When absent                        |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------- |
| `agent:claude`, `agent:opencode`                   | Which agent CLI runs the issue                                                                   | `agent:claude`                     |
| `model:opus`, `model:sonnet`, `model:go`           | A model alias from `tools/factory/factory.config.json`; a model label alone also picks its agent | The agent's default (`opus`, `go`) |
| `plan:skip`                                        | Skip planning and implement straight away                                                        | Plan first                         |
| `platform:web`, `platform:mac`, `platform:android` | Narrows which platforms need proof (CI still tests everything the path classifier selects)       | The path classifier decides        |
| `P1`–`P4` (Project 8 only)                         | Pickup order; on Linear, the issue's own priority does this                                      | P3                                 |

In Linear, `claude` and `opencode` are labels in the group **Agent**, and the model aliases are labels in the group **Model**. A group holds one label per issue, so Linear itself refuses two agents. `task factory:linear:check` lists any that are missing, and `-- --fix` creates them.

Conflicting labels (two `agent:` or two `model:` labels, or `agent:claude` with `model:go`) stop the card from starting: the daemon says why on the issue and sets Blocked, and `task factory:next` says why too.

OpenCode runs under the same sandbox as Claude Code. Its permissions come from `tools/factory/agents/opencode.json`, whose bash deny list mirrors Claude's. The factory passes that file inline with the worktree's own OpenCode config turned off, so the agent can't loosen it.

File factory work with the team's **Task** template, which asks for acceptance criteria in EARS form.

## Setup

Once, on this Mac:

0. **The checkout and the CLIs.** A checkout of `main` (`~/src/penmoss`) with Node 24 and `corepack pnpm install` done (`docs/development.md`), and `task`, `gh`, `claude` and, for `agent:opencode`, `opencode` on the PATH. Every `task factory:*` command runs from that checkout, whatever branch it is on. The daemon and the UI don't: `task factory:install` gives them a clone of their own (step 9), and the runs work in another clone under the state folder.
1. **The factory's GitHub App** (A1222). It pushes branches, opens and merges pull requests, and comments on them, as `penmoss-factory[bot]`. On GitHub, Settings, Developer settings, GitHub Apps, make a new app:
   - **Name** `penmoss-factory`. **Homepage** the repository's URL. **Webhook** off.
   - **Repository permissions:** Contents, Pull requests and Issues: Read and write. Actions, Checks, Commit statuses and Metadata: Read. Leave **Workflows** unset: GitHub then refuses any push from the factory that changes `.github/workflows`, so an agent can't change what runs on the Mac runners. A change there is yours to make. Nothing at the account level.
   - **Where can it be installed:** only on this account.

   Then **Install App** on `htxryan/penmoss` alone, and **Generate a private key**. Move the downloaded `.pem` to `~/.config/penmoss-factory/github-app.pem` and `chmod 600` it. Put the app's ID (on its settings page) and the key's path in `~/.config/penmoss-factory/github-app.env`, mode 600:

   ```
   GITHUB_APP_ID=123456
   GITHUB_APP_PRIVATE_KEY=~/.config/penmoss-factory/github-app.pem
   ```

   The key stays on the host. The factory makes an hour-long token from it for its own pushes and PRs, and a read-only one for each sandbox.

   GitHub takes PR attachments only from people, not apps, so the proof goes to Cloudflare R2 instead (A1223):

   - In the Penmoss Cloudflare account, create the R2 bucket `penmoss-factory-proof`. In its settings, under Public access, connect the custom domain `proof.penmoss.app`.
   - Under R2, Manage API tokens, create a token with **Object Read & Write** on that bucket only. Put its access key ID and secret, and the account ID, in `~/.config/penmoss-factory/proof.env`, mode 600:

     ```
     R2_ACCOUNT_ID=…
     R2_ACCESS_KEY_ID=…
     R2_SECRET_ACCESS_KEY=…
     ```

   The host uploads each run's screenshots and videos there and links them in the PR. Screenshots show inline; a video is a link to its MP4. Like the app's key, this file never reaches a sandbox.

2. **The factory's Linear app.** In Linear, Settings, API, make an OAuth application named **Penmoss Factory** with client credentials turned on. Put its client ID and secret in `~/.config/penmoss-factory/linear.env`, mode 600:

   ```
   LINEAR_CLIENT_ID=…
   LINEAR_CLIENT_SECRET=…
   ```

   The factory gets the app's token from them and acts as the app. This file is read on the host only. It is a different file from `factory.env`, so no sandbox ever sees it (LD4), and `task factory:doctor` checks that.

3. **Your own Linear key, for the Factory UI.** Make a personal API key in Linear (Settings, Security & access) and put it in your keychain: `security add-generic-password -s penmoss-factory-linear -a "$USER" -w`. The UI posts your replies and removes Blocked with it, as you. Nothing else reads it.
4. **The team.** `task factory:linear:check -- --me` prints your Linear user ID: put it in `tools/factory/factory.config.json` as `linear.owner`. Then `task factory:linear:check -- --fix` adds what the factory needs to the Penmoss team (the **Planning** state, the `Blocked`, `plan:skip` and `platform:*` labels, the Agent and Model groups), and `task factory:linear:check` should then pass.
5. **The env file.** `~/.config/penmoss-factory/factory.env`, mode 600 (`chmod 600`), with `KEY=value` lines. Only these names reach a sandbox; any other line is ignored and named (never its value) by `task factory:doctor`:

   | Name                                            | What                                     |
   | ----------------------------------------------- | ---------------------------------------- |
   | `CLAUDE_CODE_OAUTH_TOKEN`                       | from `claude setup-token`                |
   | `OPENCODE_API_KEY`                              | the OpenCode Go key                      |
   | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` | a token limited to the Penmoss account   |
   | `PLAY_SERVICE_ACCOUNT_JSON`                     | the path of the Play service account key |

6. **Trust the planning folder.** Planning sessions run from `~/Library/Application Support/penmoss-factory/plans`. Make it and run `claude` there once, accepting the trust prompt, or `claude --bg` refuses to start: `mkdir -p ~/Library/Application\ Support/penmoss-factory/plans && cd "$_" && claude`. The trust is kept by path, so it survives the factory moving old plans to `archive/` when the tracker changes.
7. **Toolchain.** The JDK, Android SDK (with the API 37 image `system-images;android-37.0;google_apis;arm64-v8a`, from which the factory makes each slot's emulator itself) and Playwright's browsers at the paths in `tools/factory/factory.config.json` (`toolchain`), and the Tart test VM for Mac proof (`docs/ci.md` §8). Optional: `brew install terminal-notifier`, so a notification opens its card in the Factory UI.
8. **Check it.** `task factory:doctor` runs with the PATH the LaunchAgents run with (not your shell's), checks that the host finds every command it runs there (`git`, `gh`, `node`, `corepack`, `claude`, `sandbox-exec`, `osascript`, `caffeinate`, `ffmpeg`, `tar`; a missing `terminal-notifier` or `opencode` is only a warning), then starts slot 1's sandbox on a throwaway branch of `origin/main` and checks the toolchain there (pnpm, Chromium, the JDK, `wrangler dev` on the slot's port block), the tokens (the GitHub check uses the app's read-only token, as a run does, and GitHub must refuse it a branch with a 403 and a push; Claude Code and OpenCode each answer a one-word prompt, OpenCode with the `opencode` agent's default model and `OPENCODE_API_KEY`; and `opencode models opencode-go` must list every OpenCode model ID in `models`, so a renamed one shows up here rather than in a run; both OpenCode checks are skipped without the key), and that your gh login, `~/.ssh`, the keychain, the Mac app's data folder (its `git-secrets.json`), the GitHub App's key, the proof bucket's key, the Linear app's credentials and your home stay out of reach, and that a relay deploy and `task site:deploy` are refused. `-- --full` adds `task check` (every step of `check:all` and every package's tests, without stopping at the first failure, so all of the sandbox's failures show in one run), the e2e smoke spec, `task android:test`, one recorded instrumented test on the slot's emulator and `task desktop:build`; `-- --slot 2` checks the other slot, and `-- --base <ref>` branches from another ref than `origin/main`. The checks themselves come from the checkout you run it in: when that checkout's commit isn't on the base, the doctor says so, since a check added on a branch can't pass against code that isn't on the base yet.
9. **Start it.** `task factory:install` clones `main` into `~/Library/Application Support/penmoss-factory/code`, runs `pnpm install --frozen-lockfile` there for the factory alone, and installs the daemon and the UI as LaunchAgents that run from that clone (A1226). Both start now and at every login, and launchd starts either again, at most every 30 s, when it exits on an error (`KeepAlive` on an unsuccessful exit, `ThrottleInterval` 30); `task factory:stop` stops the daemon cleanly, and it stays stopped until `task factory:start`, which starts whichever of the daemon and the UI isn't running. The code they run, the prompts each run reads and `factory.config.json` change only when you run `task factory:update` (Daily use), never when you switch branches in `~/src/penmoss` or delete a worktree, so a change to `factory.config.json` takes effect once it is on `main` and you update. Run `task factory:install` again after a change to the plist template or to move to another Node; it leaves the clone at its commit.

## Daily use

1. **File an issue** in the Penmoss team with the **Task** template and move it to **Todo**. Its priority sets the order; labels choose the agent, model and platforms, or skip planning (Labels, above).
2. **Planning.** The card moves to Planning and its session posts its chat link. When it has questions, it posts them on the issue and adds **Blocked**. Answer in the artifact comments, the chat, the issue or the Factory UI, then remove Blocked. Say **complete** when the plan is.
3. **Implementation** starts when a slot is free. The card moves to In Progress. The run builds on its own branch, which starts from `main` as the factory has just fetched it (a restarted run's branch keeps its commits, rebased onto that `main` when they apply cleanly). It runs the gate (`task lint` or `task check`) once the branch is rebased onto `main` and its new decisions are numbered (Decision numbers, below), records proof, validates against the plan, and opens a pull request whose body shows the proof from the R2 bucket. The PR says `Part of PEN-<n>`, so Linear shows it on the issue without moving the card: the factory moves cards itself. Its title is the branch's first commit subject (or the summary's first sentence, at most 72 characters) and never names the card, since Linear's GitHub integration moves a card named in a PR's title. Keep card IDs out of your own PRs' titles too, unless the PR finishes the card. CI goes green in the same PR. If `main` moved while CI ran, the run rebases onto it once more, runs the gate again and waits for CI again. Then the card moves to **In Review** and you get a notification.
4. **Review.** Comment on the PR or request changes: the factory answers each comment in a new round on the same branch. **Approve** to merge. The factory then squash-merges, watches `main`'s CI, says so on the issue and moves the card to Done. It deploys nothing: `main`'s CI publishes the APK and Mac builds, and production deploys (`task deploy` for the relay, `task site:deploy`) stay yours, run by hand (A1225).
5. **When `main` moves.** If GitHub says a PR in review no longer merges (it conflicts with `main`, or is behind it), the factory rebases it onto `main` in a fresh sandbox, runs the gate again, pushes and waits for CI, and says so on the PR. It does this before any CI repair or merge. When both sides only added rows to `docs/decisions.md`, as two factory PRs that each record a decision do, it keeps both, `main`'s first, and gives the PR's row a new number if `main` has taken its number. Any other conflict goes to the agent for one round; if that doesn't resolve it, the card gets **Blocked**, with the files named. If GitHub dismissed your approval when the rebase was pushed, approve again.

Whenever the factory needs you, it says why on the issue and adds **Blocked**. It never acts on a Blocked card. Add Blocked yourself to pause a card at any point: a run stops before its next step (a sandbox, the gate, a proof, a fix round, the push, the PR or the merge). A step already running, such as the gate's `task check`, finishes first, and the run's ledger and log say which step it stopped before. When you clear Blocked on an In Progress card, its run starts again on the same branch, says so on the issue, and updates its PR if it had opened one (R12). If its agent had already finished (the result it wrote, which the factory keeps in the run folder, and its commits on the branch), the run goes on from the gate instead of running the agent again.

`task factory:status` shows the commit the daemon runs (it logs it at startup too), what it is running and waiting on, and why a running card waits (the Mac proof waiting for the test VM, say). It warns when its LaunchAgent still runs from somewhere other than its own clone, and says when the daemon that wrote the status isn't running any more. `task factory:chat -- 41` opens PEN-41's planning session in the Claude app (`-- 41 --print` only prints its links). `task factory:logs` follows its log. `task factory:run -- 36` runs PEN-36 now in the foreground on slot 1 (`-- 36 --slot 2` for the other), when it is in Todo or Planning, not Blocked, and labelled `plan:skip` or has an agreed plan.

**Updating the factory.** After a factory change merges, `task factory:update` moves the daemon's clone to the latest `origin/main`, runs `pnpm install --frozen-lockfile` again, rewrites both LaunchAgents and restarts them. While a run, review round or merge is active it refuses and names them. `task factory:update -- --wait` asks the daemon to start nothing new (no planning step, run, review round or merge) and waits for what is active to finish, then updates. If the install fails, the clone goes back to the commit it had and the LaunchAgents restart on that. Both LaunchAgents are running afterwards, even if you had stopped the daemon: it waits until launchd has really let go of the old ones before loading them again, and tries a load that fails (launchd's "5: Input/output error") again a few times. It ends by printing the new daemon's first status, waiting up to two poll intervals and a minute for it. Only the daemon prepares the runs' clone and the publish repo as it starts; the UI reads the tracker and the state folder only, so the two never write the clone's config at once.

`task factory:report` shows the last seven days' throughput (started, reached In Review, merged), gate and CI rounds per issue, time from claim to In Review, and the share of issues worked that a run left Blocked. `-- --from 2026-11-01 --to 2026-11-08` picks another range (local dates; `--to` is exclusive). It reads only the run ledger, `runs.jsonl` in the state folder (each run's events, and each merge's `merged` and `done`), never the tracker, so it counts the runs' own Blocked stops, not planning questions or a Blocked you set yourself, and after a change of `tracker` it covers only the runs since (the older ledger is in `archive/`).

## Turning it off

- **Pause one card:** add Blocked.
- **Pause everything:** `task factory:stop`. Runs in progress stop. They restart on the same branch when the daemon starts again (R12).
- **Remove it:** `task factory:stop`, then `launchctl bootout gui/$(id -u)/app.penmoss.factory-ui`, and delete `~/Library/LaunchAgents/app.penmoss.factory*.plist`. Then delete `~/Library/Application Support/penmoss-factory` (the factory's own clone is in it too) and `~/.config/penmoss-factory`. Also delete the `penmoss-factory` GitHub App (or uninstall it from the repository), and the Penmoss Factory app in Linear's settings.

## Sandbox

Every run is Sandcastle's Seatbelt sandbox (`tools/factory/src/sandbox.ts`). It sees its worktree, the JDK, Android SDK and Playwright's browsers (read-only), a pnpm store, Gradle home and AVD folder the factory owns under `~/Library/Application Support/penmoss-factory`, the slot's port block (`scripts/ports.mjs`) and emulator, and the env file's tokens. It doesn't see your home, logins or caches. Four rules beyond Sandcastle's profile (Chromium's Mach rendezvous service; the `hw.` and `machdep.cpu.` sysctls the emulator reads; `kern.boottime`; and the `sysctl` command's name lookups), and a longer worktree timeout, are carried as a pnpm patch in `tools/factory/patches/`. A run sets `PENMOSS_FACTORY_RUN=1`, and the relay's deploy script refuses to run under it: production deploys happen after you merge (FD24). The Mac's heavy-job slots (W12) stay outside the sandbox: the factory takes one on the host around its gate, proof and the doctor's slow checks, and each sandbox has a one-slot folder of its own (A1216).

**GitHub from the sandbox.** An agent can't push, comment or merge. Its deny rules refuse `git push`, the clone's push URL is a dead end, and its `GH_TOKEN` is the GitHub App's read-only installation token (contents, metadata, pull requests, checks and actions, read; A1222), so GitHub refuses a push even to an explicit HTTPS URL (`task factory:doctor` checks that). Pushes, PRs and merges come from the host with the app's write token, after the gate passes. A ruleset on `main` that requires a pull request (Ryan's call) keeps even that token off `main`. The app's key, the proof bucket's key and the Linear app's credentials never enter a sandbox (`task factory:doctor` checks all three). (This replaces FD23's known gap, which came from the bot account's token.)

**Git on the host.** The host never runs git in the runs' clone (`<stateDir>/repo`) or a sandbox's worktree: a sandbox can write the top of that clone's `.git`, and a `commondir` there points git at a config of the agent's choosing (URL rewrites, push URLs, proxies). To read or publish a run, the host fetches its branch _from_ the clone into the publish repo (`<stateDir>/publish`: bare, mounted by no sandbox, with config only the host writes), refuses it unless it descends from the main the run was rebased onto, and diffs, reads and pushes there with the app's write token. Each sandbox fetches main into the clone itself as it starts, with its read-only token, and puts it at the main the host fetched into the publish repo for the run; a branch with no commits of its own (a new one, which Sandcastle makes from the clone's main) is moved onto that commit (A1232), and one with commits (a restarted run's, or a fix or review round's) is rebased onto it when its tracked files are clean and the rebase goes through; otherwise it stays where it is, for the gate's rebase. The gate sandbox fetches main and puts it there again before each rebase, and the planning snapshot is main's files exported from the publish repo. Every host git command runs without your git config (`GIT_CONFIG_GLOBAL=/dev/null`, no system config, no prompts) and with hooks, fsmonitor, credential helpers, the file transport for submodules and submodule recursion turned off (`tools/factory/src/git.ts`). The janitor runs no git: it deletes only folders directly in the clone's `.sandcastle/worktrees`, never a path that `git worktree list` names. The Mac proof runs the factory's own copy of the VM script, never the worktree's, with the worktree in `PENMOSS_VM_ROOT` (A1230).

**The gate's dependencies.** After the rebase and the decision numbers, the gate runs `pnpm install --frozen-lockfile --prefer-offline` in its checkout, then the check. The rebase can bring in main's changed lockfile, and without the install the check ran on modules the agent installed for the old one (A1251). A failed install goes back to the agent like a failed check.

**Decision numbers.** An agent records a decision as a new row `| A-NEW-n |` in `docs/decisions.md`, and the factory gives it a real number after the gate's rebase, before the gate runs: the next one after `main`'s highest and the highest it has already given out (the `decision-numbers` file in the state folder, so two slots never take the same one). It reads what the branch added in the publish repo (`git diff` from the run's base) and numbers only that: a placeholder is defined by a row the branch added, and gets its number in that row and in the branch's other added lines that name it, outside `tools/factory/`. A placeholder in text the branch didn't add, such as the instructions in `AGENTS.md` and the prompts, or one the branch never defined, stays as it is. The numbers go in one more commit; a branch with no new decision gets no commit and reserves nothing (A1232). A number `main` takes meanwhile is moved on after a later rebase (A1228). Then it formats `docs/decisions.md` with Prettier, using its own settings, since a number is narrower than the placeholder an agent's Prettier padded the table for. A decision added by hand while runs are open takes a number from the same counter: set `decision-numbers` to it (A1248). When main has gained a decision since the branch's base, the gate's rebase merges `docs/decisions.md` itself, also when the branch's Prettier re-padded the whole table: it merges the three versions with each cell's padding taken out, then formats the result (A1250). An edit of the same row on both sides still goes to the agent. When the gate's check fails, the run folder keeps its whole output as `gate.log`, and the feedback shows the error lines, then the last 30.

## Proof

After the gate passes, the harness records each in-scope platform's proof specs itself (`.factory/result.json` names them), holding one of the Mac's heavy-job slots. Each platform's recording has `timeouts.proofMinutes` (40). At the timeout the factory stops what the proof started, not only the wait for it: a command it runs on the host gets its own process group, which gets SIGTERM, then SIGKILL a grace later, and so does the group if the daemon itself dies mid-proof (`tools/factory/src/exec.ts`).

- **Mac** runs in the test VM (`scripts/vm/desktop-test.sh`, `docs/ci.md` §8), which only the host can start. The host runs the factory's own copy of the script, which copies the run's worktree (`PENMOSS_VM_ROOT`) into the VM. Before it, the factory asks the script's `--check` whether the VM can take a run now. While it can't (`tart` missing, the VM `macProof.vm` not made, another run on it, a VM started by hand, or a boot that didn't answer: the script's exit 75), the run waits without failing or using a gate round, asks again every poll, and `task factory:status` shows the reason. The waits hold no heavy-job slot. After `macProof.waitHours` (12) it stops, Blocked, with the reason. At the proof timeout the script is stopped with its `tart run`; its trap stops the VM, which frees the VM's lock for the next run.
- **Android** runs on the slot's own emulator, in its sandbox. `am instrument -w` has no timeout of its own and waits as long as a hung test does, so at the proof timeout the host stops the slot's emulator, which ends it, and closing the sandbox ends the rest. Before each Android proof the host also stops an emulator a stopped run left on the slot's port and removes the AVD's stale lock files, so the next boot isn't refused.

## Planning

A Todo card (Ready on Project 8) without `plan:skip` moves to Planning. Planning doesn't take a slot. The daemon starts one background Claude session for the card (`claude --bg --remote-control "Penmoss PEN-41 plan"`, named after the card as the active tracker numbers it). The session reads a snapshot of `main`, can write only to its own output folder, and has no MCP servers and no Chrome. It publishes the plan, plus a design if what users see changes, as artifacts. The daemon posts its chat link on the issue, and posts the new one each time it resumes the session, since each resume gets a new link. On every poll the daemon reads the session's `state.json`:

- **Waiting on you.** The daemon posts the open points with the links, sets Blocked and stops the session. Questions with a few clear answers list them, so you can pick one in the Factory UI. Answer in the artifact comments, the chat or on the issue, then clear Blocked. The session resumes with your issue comments and checks the artifact for the rest. Anyone else's new comments go along fenced as untrusted data (R14): they never resume the session or end planning.
- **Agreed.** Only an explicit yes ("complete", "agreed", "go") counts; "looks good, but…" is feedback. A yes as an issue comment counts too. When the session reports a yes on the issue, the daemon checks your own comment there holds the words it quotes; if none does, it asks you instead. The daemon keeps a copy of `plan.html` that later edits can't change and stops the session. The card implements next, with that plan in the prompt, ahead of new Todo cards.
- **Trivial.** The session may judge an issue too small to plan (`planning.agentMaySkipTrivial`). The daemon says why on the issue and implements it.
- **Quiet.** If the session is idle for 10 minutes without writing its state, the daemon says so and sets Blocked.

The daemon never acts on a card while Blocked is set, not even on a yes.

## Validation

When a planned change reaches the web, the gate and proof run first, then validation. One agent session starts the app on the slot's port block. It walks each acceptance criterion and screenshots it next to the agreed mockup rendered at the same size. A second, independent session compares each pair and gives a verdict: match, mismatch or deviation. It also reads what the builder said it couldn't do and why (`risks` in `.factory/result.json`), so a reason that holds becomes a deviation with that reason. A mismatch goes back to the builder, using the gate's fix rounds. Whatever is still wrong after the last round goes in the PR as a deviation. The PR shows a fidelity table with each mockup beside its screenshot. Mac and Android walkthroughs come with F7 and F8.

## Factory UI

`task factory:install` also starts the UI at login: a page on `127.0.0.1:7878` (`task factory:ui:open`; `task factory:ui` serves it in the foreground when its LaunchAgent isn't running). It updates itself every few seconds and has two views, switched in its header (A1233):

- **Inbox:** what needs you, oldest first, each with what to do (answer the plan, review the PR, unblock, fix the Mac, fix the card); then what the factory is working on, the queue in pickup order, and the slots' runs over the last 12 hours. The card you pick (the oldest, until you pick another) opens beside the list.
- **Pipeline:** a row per card and a column per step (Todo, Plan, Build, Gate, Proof, PR + CI, Review, Merge, Done), with a coloured marker on the card's step: blue while the factory works, amber when it's your turn, red when it stopped, purple when it won't start, grey when queued or paused. Clicking a row opens the same detail as the Inbox.

The detail says what the card is doing in the factory's words, or why it stopped (a run that failed before the agent started says so, with the error and the command that fixes it), its runs, the last lines of a live run's agent log, the run folder's path, and its links: the issue, pull request, CI, the plan and design artifacts, the planning chat, and **Open in Claude**, which opens that session in the desktop app.

Only the factory's own cards are shown: Todo and Planning cards, and In Progress, In Review or Done cards whose claim is in the run ledger (`runs.jsonl`). An In Progress card the factory never claimed, such as a task you're doing yourself, is counted in one line, not listed. A card you set Blocked on yourself is paused, in the queue, not in Needs you.

The header is the factory's health: the daemon's pid, its commit, when it last polled, its slots and the doctor's last result per slot. When the daemon's pid has exited, or it hasn't polled for three intervals, the header says so, with the command to run, and the rest of the page is dimmed: it is as of the last poll. The page also names a daemon running from the wrong checkout and a failing doctor check. At phone width it's one column, and a notification's link opens on its card.

From the page you can also reply on an issue (and clear Blocked in the same click), pick one of the planning session's proposed answers, say **Complete** to agree the plan, and set or clear Blocked. These writes use your own Linear key from the keychain item `penmoss-factory-linear` (Setup, step 3), never the factory app's, so they appear as yours. Without that key, or when it doesn't answer as `linear.owner`, the page is read-only: it says why, and its buttons stay off. On Project 8 the writes use your own `gh` login instead, and the page is read-only unless it is signed in as `htxryan`. A card that Linear holds only because an unfinished **blocked by** issue waits in the queue and names that issue; it has no Blocked to clear, but you can still set Blocked on it. The daemon can set Blocked but has no code that clears it; a test keeps the UI's writer out of the daemon.

Each launch makes a new token. The link carries it once, then a cookie does, including when you tap the link in another app (A1249). Requests without it, from another `Origin` or for another `Host` get 403. The UI listens on no other interface. To open it on your phone or another of your devices, run `task factory:ui:tailnet` once: Tailscale serves it on your tailnet at `https://<this Mac>.<tailnet>.ts.net:8443` (never Funnel, so never the internet), and the UI accepts that name too; `ui.log` gives the link with its token (A1246). `tailscale serve --https=8443 off` turns it off. With [`terminal-notifier`](https://github.com/julienXX/terminal-notifier) installed (`brew install terminal-notifier`), clicking a factory notification opens its card.

There is no pause button for the whole factory yet: pause one card with Blocked, or stop the daemon (Turning it off). The page shows a run's folder as a path to copy rather than revealing it in Finder.

The page's own check runs headless Chromium against a fake state folder: `pnpm --filter @penmoss/factory e2e` (A1234). It never opens a window on the Mac.
