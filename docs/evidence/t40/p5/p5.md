# T40 P5 · Daily and weekly notes on Android

Evidence for the fifth slice of T40's P5 ([issue #76](https://github.com/htxryan/penmoss/issues/76)), as amended by the PR #98 review:

- Offline Today and This week, made by the editor page (JR1, JR2): a `createPeriodic` bridge message builds the note exactly as the web does — deterministic derived id, template from the synced settings (ST2), synced time zone — and answers `createdPeriodic`; the phone stores it as one pending edit, files it through a queued `POST /api/daily` intent, and the note's screen replaces the transient one. A note the phone lists is the server's: one not fetched yet is fetched by its screen (offline: unavailable), never rebuilt from the phone's template; a note in Trash comes back at once, as on the web.
- The Journal calendar (JR3): a month grid with dots under days that have daily notes, an ISO week-number column and a Today chip that opens today's note; days and weeks named for TalkBack as the web names them; marks from Room, offline too.
- Previous and next day-week navigation (JR4): a row under the top bar with the previous, the period's name, next, and the week (or the week's seven days).
- Server: `kind` and `period` in `/sync/changes` and `/sync/tree` (the tree's from the `notes_period` index, read only when the tree is sent).

Decisions A450–A459 are in [`decisions.md`](../../../decisions.md).

## How it was run

- **No emulator session: blocked on KVM.** As in P3b and P4, the worker's `penmoss36` AVD exists but this session's user has no KVM permission, so the emulator never boots. The Pixel checklist (in [`docs/android.md`](../../../android.md#test-daily-and-weekly-notes-on-the-pixel-t40-p5)) is for Ryan, and the flows it checks are covered by the tests below.
- **What covers it instead:**
  - Server route tests in workerd (`android-sync.test.ts`, +3): kind and period in `/sync/changes` for a daily and a weekly note; in `/sync/tree` for journal notes only; an unchanged tree poll reads nothing from D1 and a full read asks it once; the journal query's plan uses `notes_period`.
  - Page tests (`@penmoss/android-editor`, 99 in 10 files): `createPeriodic` answers the shared fixture's id and update bytes for an explicit day, for a weekly note reached from a day in its week and for today at a fixed instant, and other bytes for another template; it reads today in the synced zone with the device in Tokyo, resolves weeks and falls back for an unknown zone, and answers an error for a bad day. `periodicNav` names daily and weekly neighbours in the web's words and null for regular notes. The contract suite reads the `createPeriodic`/`createdPeriodic`/`periodicNav` fixtures both ways, as does Kotlin's `BridgeProtocolTest`. `periodic-fixture.test.ts` pins the bytes `periodicNote` builds (also read by the web's `periodic.test.ts`), and `journal-calendar-contract.test.ts` writes `journal-calendar-v1.json` from core for Kotlin's `JournalTest`.
  - Kotlin (`engine-bridge`): `BridgeProtocolTest` (malformed periodic messages, and a `createdPeriodic` whose note title is not its period), `HttpPenmossApiTest` (+1 daily intent body).
  - Robolectric store tests (`JournalStoreTest`, 15): the intent waits with kind/period/date; Today twice offline makes one note; kind backfill; a note trashed here after it was made keeps its intent; Today on a note trashed elsewhere, trashed here and not sent, and moved to Trash by the server for this phone (each restored here at once and filed), and moved then trashed here (the move kept); a listed note without its content storing nothing; a purged note made afresh with its kept-apart edits and base untouched; an older server's changes row keeping Room's kind; kind and period from changes and the tree; marks leaving out Trash and purged notes; a move replacing the intent.
  - Robolectric sync tests (`JournalSyncTest`, 6, through the real coordinator, engine, store, filer, Trash sender and HTTP client against `FakePenmoss`): offline Today filed under `Journal/2026/10` with calendar marks, This week under `Journal/2026/Weekly`, a trashed daily the phone did not hold restored by filing, a held daily trashed elsewhere restored by an offline Today, an online open of a listed, unfetched daily uploading none of the page's bytes and fetching the server's content unchanged, marks from the tree and changes. The fake server records any daily intent that arrives before the note's content, and every test expects none.
  - Robolectric filer tests (`NoteFilerTest`, +4): the intent's explicit day and kind, offline retry, refusal dropped, a 404 dropped.
  - Robolectric controller tests (`NoteEditorControllerTest`, +4): the page asked with the synced zone and template (and again on reload), stored and filed once with the made callback either way, UNAVAILABLE when the page cannot make it, the period asked once per open.
  - Robolectric navigation tests (`PeriodicNavigationTest`, 2, through the app's own `PenmossNavHost` and its slide transitions): Today ends on the note's screen and Back returns Home; a note made after Back opens nothing.
  - Model tests (`JournalTest`, 7): the October 2026 grid, New Year weeks, month steps, mark splitting, today at a fixed instant, and against core's contract every month's weeks, days and spoken names, and today either side of the midnights around both DST changes.
  - Robolectric UI tests (`JournalScreensTest`, 4, real clicks hit-tested at each node's centre): the month grid with marks, its spoken names, day/week taps (the week resolving to its Monday) and the Today chip; month arrows; the period row's labels and taps for a daily and a weekly note.
  - `ScreensTest` (Today and This week buttons, All notes and Journal in the overflow menu), `MigrationTest` (+1: schema 11 opens at 12 with kind `note`, no intents, no tree hash, its changes cursor kept, and the next tree marks its journal notes).
  - Full `task android:test` (735 JVM/Robolectric tests: 103 `engine-bridge`, 632 `app`; 0 failures), `task android:build`, `task typecheck`, and `task check` (lint, typecheck, every package suite, releases test), including the server suite in workerd (39 files, 643 tests, 0 failures): all green.

## Walk-through (by test, against the canned servers)

| Step | What happens |
| --- | --- |
| Today | Home → **Today**: the periodic screen makes the day's note from the synced template in the synced zone (`asksThePageForThePeriodsNoteWithTheSyncedTimeZoneAndTemplate`, `storesThePeriodsNoteFilesItThroughTheDailyIntentAndOpensIt`), and the note's screen replaces it, Back returning Home (`todayOpensTheMadeNoteAndBackReturnsHome`). A second tap while offline opens the same note, with nothing stored twice (`todayTwiceOfflineMakesOneNote`). A note the phone lists without its content (made on the web, not prefetched) stores nothing from the page: its screen fetches the server's note, and nothing is uploaded (`todayOnAListedNoteWithoutItsContentStoresNothing`, `anOnlineOpenOfAListedUnfetchedDailyNoteUploadsNoPageBytes`); offline it is unavailable, with Retry. |
| This week | Home → **This week**: the week's note, the same way (`thisWeekMadeOfflineFilesUnderTheWeeklyFolder`). |
| Calendar | Home ⋮ → **Journal**: the current month with dots under days that have daily notes and marked week numbers (`theCalendarShowsAMonthWithMarksAndOpensDaysAndWeeks`, `calendarMarksComeFromTheTreeAndChanges`). A day opens or creates that day's note; a week number opens or creates that week's (`week:2026-10-19` for the tap on `2026-W43`). Arrows move between months; **Today** opens today's note, as the web's does. TalkBack reads "Wednesday 21 October 2026, has a note" and "Week 2026-W43, has a note" (`theCalendarShowsAMonthWithMarksAndOpensDaysAndWeeks`). |
| Period navigation | On a daily note, a row under the top bar: ‹ previous day, the long date, next day ›, and a Week chip (`thePeriodRowShowsThePeriodAndItsNeighbours`). On a weekly note: the week with the previous and next weeks and seven day chips (`thePeriodRowShowsAWeeksSevenDays`). Every tap opens through the page again, so DST and ISO-week edges run core's functions. |
| Filing | In airplane mode, make Today's note and type a line; Settings → Sync and storage lists the waiting daily intent. Back online and Sync now: the content uploads, then `POST /api/daily {"date":"2026-10-21","period":"daily"}` files it under `Journal/2026/10`; the tree files it there on the next pass and the calendar marks it (`todayMadeOfflineIsFiledUnderJournalOnceOnline`). A daily note in Trash is restored by filing it (`filingRestoresADailyNoteInTrash`). |
| Trash | Today on a held daily note in Trash takes it out of Trash on the phone at once, offline too, with its calendar dot, then restores it on the server and files it under Journal: trashed on the web (`todayOnAHeldDailyNoteTrashedElsewhereRestoresItEverywhere`, `todayOnANoteTrashedElsewhereRestoresItHereAndFilesIt`), trashed here and not sent (the move is cancelled, `todayOnANoteTrashedHereAndNotSentCancelsTheMove`), and trashed here and confirmed (a restore is queued, `todayOnANoteTheServerMovedToTrashForThisPhoneQueuesARestore`). A note deleted for good is made afresh, its kept-apart edits still to become their conflict copy (`todayOnANoteDeletedForGoodMakesItAfreshAndKeepsTheEditsKeptApart`). |
| Offline and sign-out | The periodic screen, the calendar and its marks all work in airplane mode (Room only). The intent survives sign-out (`readyToFile` counts as unsent, as moves do); a restoring intent is on a note out of Trash, so it is counted too. |
| Older servers | Against a server from before these fields, the calendar stays empty (older `/sync/changes` and `/sync/tree` send neither, and Room keeps its defaults); Today still files through the daily route, which is old, and a changes row without a kind leaves what Room holds (`aChangesRowFromAnOlderServerKeepsTheKindRoomHolds`). Sync and storage lists the waiting daily intent (A459). |
| Upgrade after the deploy | The 11→12 migration clears the stored tree hash, so the next pass reads the whole tree and marks every existing journal note (`aT40P4BuildsSchema11OpensWithNotesAndNoDailyIntents`). |

**Not walked through on a device:**

- **Finger taps on a device** (JR3, JR4): `JournalScreensTest` taps the period row, the week-number column and day cells with `performClick`, which hit-tests at each node's centre, so a target covered by another fails. An earlier draft clicked through the semantics action instead, because `performClick` landed on the wrong targets in the period-row tests (Prev opened the Week chip). The cause: `PeriodNavRow` emitted two sibling rows and relied on the caller's `Column`; in the bare test host they stacked at the origin and the chip row took the touch. On the note screen it sits inside a `Column`, so the app was right, but the row now has a `Column` of its own and the tests use real clicks. TalkBack order and large-text layouts are in the Pixel checklist.
- **The midnight race** (making Today at 23:59, filing at 00:01): the intent always carries the explicit day the page resolved, so filing targets the same note (`fileDate`, `aDailyIntent...`); covered by unit tests, checked by hand on the Pixel.
- **TalkBack order on the calendar**: the spoken names are pinned by `JournalScreensTest`; the reading order is checked by hand on the Pixel.

## Deploy

This slice has a server half: `kind` and `period` in `/sync/changes` and `/sync/tree`. **Deploy before the Pixel checklist in [`docs/android.md`](../../../android.md#test-daily-and-weekly-notes-on-the-pixel-t40-p5)** (A459), then install the APK: its migration reads the whole tree once, so journal notes made before the upgrade are marked. The deploy itself changes no phone's tree hash, since kinds are out of it. Installed before the deploy instead, the APK's one full read reaches the old server, which sends no kinds, so existing journal notes stay unmarked until the tree next changes (any note made, moved or trashed); notes indexed after the deploy mark through `/sync/changes` (A459, re-review R-N2).
