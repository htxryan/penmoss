# F0.1 spike: headless agents on the installed versions

Gathered from the factory's own runs and doctor checks, 8–10 Nov 2026: Claude Code 2.1.322 and OpenCode 2 on OpenCode Go, each started by Sandcastle inside a slot's Seatbelt sandbox with the factory's tokens. The question: how does the factory run each agent headless, what does it get back, and do its deny rules hold with permissions skipped?

**Status: both agents run headless with JSON streams and session IDs, and both refuse `git push` with the factory's settings. A usage limit hasn't been seen live; how the factory reads one is below.**

## Usage limits

Not seen live. Claude Code reports a usage limit in its closing `result` event, as an error (`is_error: true`) whose text is `Claude AI usage limit reached|<epoch>` or "… resets 3pm". The factory reads a limit only from that event when the session has one (A1274), and otherwise from what the session added to `agent.log` (A1273). It then waits for the reset and runs the same round again without using one up (R13, `runAgentPatiently`). PEN-93 (10 Nov) exercised the pause and resume live, from a false trigger that A1274 then removed. For OpenCode, any rate-limit message gets a 30-minute wait.

## What this means for the design

- Both agents run under Sandcastle with JSON streams. The factory reads progress and results from `.factory/result.json`, never from the stream, and keeps the stream only as the transcript.
- The deny rules are a second line. The first is the sandbox's read-only GitHub token, so a push that slipped past the rules would still get a 403 (doctor check "a push with the sandbox's token is refused (A1222)").
- The doctor now checks both agents' deny rules live, so a renamed tool (OpenCode's `bash` to `shell`) or a changed flag shows up in `task factory:doctor`, not in a run.
